## 1. 문서 목적과 현재 상태

이 문서는 2026-08-20 `develop`의 `bc55131` 기준으로 계약과 실제 구현을 대조한 현황 문서다. 새로운 제품·API·DB 계약을 만들지 않으며, 충돌 시 아래 상위 문서를 따른다.

1. [`AGENTS.md`](../AGENTS.md)
2. [`docs/requirements/요구사항_정의서.ndjson`](../docs/requirements/요구사항_정의서.ndjson)
3. [`docs/MVP_SCOPE.md`](../docs/MVP_SCOPE.md)
4. [`docs/DOMAIN_RULES.md`](../docs/DOMAIN_RULES.md)
5. [`docs/API_CONTRACT.md`](../docs/API_CONTRACT.md), [`docs/DATA_MODEL.md`](../docs/DATA_MODEL.md)
6. [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md), [`docs/TECHNICAL_PLAN.md`](../docs/TECHNICAL_PLAN.md)
7. [`docs/IMPLEMENTATION_PLAN.md`](../docs/IMPLEMENTATION_PLAN.md)

현재 구현 상태는 다음과 같다.

- FastAPI 공통 기반뿐 아니라 온보딩, 프로필·동의, 카탈로그, 루틴, 일일 체크인, 결정 파이프라인, 운동 실행, 주간 리포트·다음 계획, 계정 삭제가 `develop`에 병합돼 있다.
- 실제 OpenAPI에는 `/api/v1` 아래 34개 operation이 등록돼 있고, DB migration은 `0001_backend_baseline`부터 `0022_promote_merged_data`까지 단일 chain이다.
- 운동 카탈로그와 처방 데이터는 PR #101에서 병합 데이터 적재·승격까지 반영됐다. 추천 시에는 활성 catalog version과 승인 상태 검사를 계속 적용한다.
- 웨어러블 provider·API·저장 흐름은 구현되지 않았다. 수동 체크인과 앱 운동 블록 경로만 동작한다.
- 캘린더는 계약, 결정 규칙, provider port, DB model/repository까지만 구현됐다. 공개 API와 실제 provider adapter는 없으며 PR #96에서 수동 가능시간 입력으로 명시 보류됐다.
- Firebase ID token 검증과 내부 identity 연결은 구현됐지만 Google·Kakao·Naver 각각의 서버 측 social exchange adapter/API는 완성되지 않았다.
- 저장소에서 확인한 백엔드 테스트는 72개 파일의 test 함수 594개이며 parametrization을 적용한 non-integration 수집 결과는 821개다. 이번 문서 작업에서는 808개가 통과했고 `tmp_path` 13개는 Windows 임시 폴더 ACL 때문에 setup 단계에서 실행되지 못했다.

### 1.1 상태 판정 기준

| 상태 | 의미 |
|---|---|
| `IMPLEMENTED` | 필요한 계약, 실행 코드, 저장 경계(해당 시), 테스트, 병합 PR 근거가 모두 `develop`에 있음 |
| `PARTIAL` | 핵심 흐름 일부는 동작하지만 하위 AC 또는 provider·운영 경로가 남아 있음 |
| `DEFERRED` | MVP 요구는 유지하지만 명시적 보류 결정이나 외부 선행조건 때문에 실행 경로가 없음 |
| `MVP_EXCLUDED` | 요구사항 문서에서 MVP 이후로 분리되어 현재 구현·완료 판정 대상이 아님 |

상위 기능 상태는 하위 AC 중 가장 낮은 상태를 따른다. model·repository 또는 UI mock만 존재하는 경우
`IMPLEMENTED`로 올리지 않는다.

## 2. 기존 문서에서 바로잡은 핵심 기준

| 항목 | 최신 구현 기준 |
|---|---|
| 이용 연령 | `date_of_birth`를 필수로 받아 암호화 저장하고 사용자 timezone의 로컬 날짜로 만 14세 이상을 서버에서 검증한다. 만 나이는 저장하지 않는다. |
| 생년월일 사용 제한 | 생년월일과 만 나이는 로그·분석·LLM·에이전트·decision snapshot에 넣지 않는다. 프로필에는 서버가 일시 계산한 `age`만 표시한다. |
| 멀티에이전트 | `TrainingAgent`, `RecoveryAgent`, `SafetyAgent`, `FeasibilityAgent` 네 proposal을 공통 입력·기본 후보로 병렬 실행하고 `Coordinator`가 최종 루틴 한 개를 결정한다. |
| 안전 흐름 | 별도 `SafetyPrecheck`나 독립 `FinalSafetyGate`를 두지 않는다. `SafetyAgent`의 `PASS/NEEDS_INPUT/REVISE/BLOCKED` 의견과 결정적 안전 veto를 Coordinator가 반영한다. |
| 공개 선택지 | 운동 계획은 `FINAL_ROUTINE` 한 개만 공개한다. 내부 `ORIGINAL`, `lighter`, 안전 veto 후보는 공개하지 않는다. 운동 추천과 함께 별도 `REST` opt-out을 제공할 수 있다. |
| 요청 시간 | 사용자의 명시적 `USER_OVERRIDE`가 없으면 `requested_duration_minutes`를 바꾸지 않는다. 계획을 반환하면 `estimated_duration_seconds = requested_duration_minutes * 60`이어야 한다. |
| 수행 완료 | 경과 시간·웨어러블·캘린더 결과가 아니라 사용자가 명시적으로 완료한 운동 블록 상태로만 공식 세션 상태를 계산한다. |
| 웨어러블 | 요약 연동은 MVP다. 제공자 미연동·권한 거부·API 오류에도 수동 체크인과 앱 운동 블록 경로가 계속 동작해야 한다. |
| 캘린더 | 빈 시간 후보, 운동 계획 등록, 등록 일정의 수행 여부 확인은 MVP다. 캘린더 결과는 공식 수행 상태를 변경하지 않는다. |
| 수동 외부 운동 기록 | MVP에서 제외한다. 세션 안의 계획 외 추가 운동 기록과 세션 밖 수동 외부 운동 기록을 구분한다. |
| LLM | 선택적 설명 생성만 담당한다. 계획·시간·안전·후보 선택을 변경할 수 없고 실패 시 같은 결정과 검수 템플릿을 반환한다. |
| 데이터 승인 | 파이프라인의 `DOMAIN_APPROVED` 표기는 생성기 호환 상태일 뿐 전문가 운영 승인이 아니다. `production_eligible=false`이면 사용자 계획에 사용할 수 없다. |
| 주간 폐쇄 루프 | 닫힌 주 리포트를 요청 시 생성하고 사용자의 명시적 acknowledgement 전에는 다음 주 계획을 최종 확정하지 않는다. 콜드스타트 첫 주만 예외다. |

## 3. 시스템과 모듈 경계

백엔드는 Python 3.12+, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 기반 모듈형 모놀리스다. API 요청 안에서 결정 파이프라인을 동기 실행하며 Redis, Celery, Kafka, LangGraph, 벡터 DB, 에이전트별 마이크로서비스는 기본 구성에 넣지 않는다.

| 모듈 | 백엔드 책임 | 금지 사항 |
|---|---|---|
| `core` | 설정 검증, 공통 오류, 요청 ID, 민감정보 제거 로깅 | 비즈니스·안전 규칙 |
| `identity` | Firebase ID Token 검증 결과와 내부 사용자 연결, 소셜 adapter, 삭제 대기 접근 차단 | provider token의 도메인 DB 저장 |
| `profiles` | 온보딩, 생년월일 적격성, 장비·주의 부위·선호, 동의 현재 상태와 이력 | 나이 파생값 저장, 의료 상태 추론 |
| `catalog` | 검수 상태·출처·라이선스가 있는 운동, 대체 관계, 안전 규칙 조회 | 미승인 seed의 사용자 추천 사용 |
| `routines` | 콜드스타트·기본·주간 루틴과 불변 버전 관리 | route 안의 루틴 생성 규칙 |
| `checkins` | 사용자 직접 입력 당일 컨텍스트의 생성·교체·버전 관리 | 누락값으로 건강 상태 추정 |
| `decisions` | 입력 snapshot, 공통 후보, 네 proposal, Coordinator, 안전 의견 반영, 원자적 저장 | 자유 형식 운동 생성, 독립 final safety gate 추가 |
| `workouts` | option 선택, 세션, 블록 상태, 타이머 이력, 안전 이벤트, 종료·미수행·피드백 | 시간·웨어러블 기반 공식 완료 |
| `weekly_reports` | 월–일 경계, 논리적 마감, 리포트, acknowledgement, 다음 계획 게이트 | 열린 주의 최종 리포트 생성 |
| `integrations` | Firebase, Google/Kakao/Naver, 웨어러블, 캘린더, 선택적 LLM adapter | 외부 SDK 타입을 domain에 노출 |
| `db` | SQLAlchemy 모델, repository, transaction 지원, Alembic | repository 안의 도메인 결정 |

의존 방향은 `api -> application service -> domain -> port`다. repository와 integration은 port를 구현하며 domain은 FastAPI, ORM, Firebase SDK, LLM SDK를 import하지 않는다.

## 5. 결정 파이프라인과 실패 계약

```text
정규화된 최소 입력 snapshot + 검수된 공통 기본 후보
  ├─ TrainingAgent
  ├─ RecoveryAgent
  ├─ SafetyAgent
  └─ FeasibilityAgent
          ↓ 병렬 proposal 4개
결정적 Coordinator
          ↓
후보·proposal·Safety 의견·최종 결정 원자적 저장
          ↓
검수 템플릿 또는 선택적 LLM 설명
```

- 네 proposal 중 하나라도 누락되거나 `FAILED`이면 decision run 전체가 `FAILED`다.
- `SafetyAgent`의 `BLOCKED`와 결정적 안전 veto는 다른 proposal이나 Coordinator가 완화할 수 없다.
- 독립적인 최종 Safety 재검사 단계와 결과는 실행·저장·공개하지 않는다.
- proposal 상세 JSON과 공개 요약 필드는 잠정 계약이다. 증상 사용자 시나리오 검증 결과와 승인된 계약 없이 임의 확장하지 않는다.
- 성공 응답 전에 입력 snapshot, 후보, 네 proposal, Safety 의견, 최종 결과가 재현 가능하게 저장돼야 한다.

| 안전 상태 | API 결과 | 계획 |
|---|---|---|
| `PASS` | 정상 `DecisionResponse` | 최종 추천 계획 1개 |
| `REVISE` | 정상 `DecisionResponse` | 안전 조정이 반영된 계획 1개 |
| `BLOCKED` | 정상 `DecisionResponse` | `REST` 또는 `STOP_AND_SEEK_HELP`, 계획 없음 |
| `NEEDS_INPUT` | `422 NEEDS_INPUT` | 없음 |
| `FAILED` | `500/503 DECISION_FAILED` | 없음 |

## 6. 실제 공개 API

`backend.app.main:app`의 OpenAPI를 기준으로 34개 operation이 등록돼 있다.

| 영역 | 구현 endpoint |
|---|---|
| 상태 | `GET /api/v1/health/live`, `GET /api/v1/health/ready` |
| 사용자 | `GET /api/v1/me`, `PUT /api/v1/me/onboarding`, `PATCH /api/v1/me/profile`, `GET/PUT /api/v1/me/consents`, `DELETE /api/v1/me` |
| 운동·루틴 | `GET /api/v1/exercises`, `GET /api/v1/exercises/{exercise_id}`, `POST /api/v1/routines`, `GET /api/v1/routines/current` |
| 체크인·결정 | `PUT/GET /api/v1/daily-contexts/{local_date}`, `POST/GET /api/v1/decisions`, `GET /api/v1/decisions/{decision_id}`, `POST /api/v1/decisions/{decision_id}/selection` |
| 운동 세션 조회 | `GET /api/v1/workout-sessions`, `GET /api/v1/workout-sessions/{session_id}` |
| 운동 세션 mutation | `PATCH .../start`, `PATCH .../items/{plan_item_id}`, `POST .../timer-events`, `POST .../additional-activities`, `POST .../safety-events`, `PATCH .../finish`, `PATCH .../not-completed`, `POST .../feedback` |
| 주간 폐쇄 루프 | `GET /api/v1/weeks/{week_start}`, `POST .../report`, `POST .../plan`, `POST .../plan-revisions`, `GET /api/v1/weekly-reports/{report_id}`, `POST .../acknowledgement` |

다음 계약 또는 계획 endpoint는 현재 OpenAPI에 없으므로 구현 완료로 간주하지 않는다.

- `POST /api/v1/auth/social/{provider_code}/exchange`, `GET /api/v1/me/identities`
- `/api/v1/wearables/**`
- `/api/v1/calendar/**`

전체 request·response·오류·null 규칙은 [`docs/API_CONTRACT.md`](../docs/API_CONTRACT.md)를 기준으로
한다. 계약 문서에 endpoint가 있어도 OpenAPI·service·저장·테스트가 연결되지 않으면 `PARTIAL` 또는
`DEFERRED`다. 카탈로그 관리자 CRUD, 클라이언트 웨어러블 요약 mutation, 수동 외부 운동 기록 API는
MVP 공개 계약이 아니다.

## 7. 영속화와 트랜잭션 경계

- PostgreSQL이 단일 진실 공급원이다.
- DB 접근은 repository, use case와 transaction은 application service가 소유한다.
- 스키마 변경은 [`docs/DATA_MODEL.md`](../docs/DATA_MODEL.md) 갱신, Alembic migration, rollback 또는 forward-fix 설명과 함께 진행한다.
- 주요 관계·검색·제약 필드는 typed column으로 두고 JSONB는 input snapshot, proposal, 확장 metadata에 제한한다.
- `decision_runs`, `agent_proposals`, `plan_candidates`, `safety_reviews`, `decision_options`, `decision_selections`를 분리한다.
- 동의 현재 상태 갱신과 동의 event append는 한 트랜잭션이다.
- decision 기록 저장 실패, 리포트 집계 저장 실패, 다음 계획 게이트 실패는 성공 응답으로 바꾸지 않는다.
- 결정 재현에는 input schema, routine, catalog, policy, safety rules, duration rules, graph, coordinator version을 저장한다. LLM을 사용한 경우에만 model·prompt version을 저장한다.

## 8. 데이터 파이프라인 인계 기준

현재 고정 산출물은 다음과 같다.

- 병합 카탈로그 `merged-mvp-v0.4.0`: 운동 56종
- 안전 규칙 `merged-mvp-v0.5.0`: 282건
- 대체 관계 `merged-mvp-v0.4.0`: 238건
- 처방 `merged-mvp-v0.1.0`: goal tag 32건, prescription profile 36건
- 출처·라이선스·수집 시각·원본 해시·재현 매니페스트

generated manifest는 DRAFT와 `production_eligible=false`를 유지한다. 운영 승격은 importer가
아니라 migration 0022의 고정 version/hash/count와 승인 코드 검증, 이후 명시적
`catalog_activate` 절차로만 수행한다.

사용 조건:

| 용도 | 허용 여부 | 조건 |
|---|---|---|
| importer·schema·repository 개발 | 허용 | 비운영 환경, DRAFT·출처·버전 보존 |
| 합성 통합 테스트·fixture | 허용 | 실제 사용자 데이터와 혼합 금지 |
| 프로덕션 추천·사용자 노출 | 조건부 허용 | migration 0022 승인 증적과 활성화 검증을 모두 통과한 정확한 version/hash/count만 허용 |
| 안전 임계값 확정 근거 | 금지 | 외부 운동·보건 검수와 승인 증적 필요 |

새 버전은 다시 DRAFT로 시작한다. 기존 승인 코드를 재사용하거나 manifest의
`production_eligible=false`를 직접 수정해 승격하지 않는다.

## 10. 필수 테스트와 완료 기준

수정 영역에 맞는 formatter, linter, type checker, unit, API, repository·integration test를 실제 실행한다. 규칙·에이전트 변경에는 golden, safety invariant, LLM fallback, reproducibility test를 추가한다.

최소 필수 시나리오:

1. 정상 상태의 `KEEP`
2. 40분 요청과 CORE를 보존하는 `DOWNSHIFT`
3. 사용자 `USER_OVERRIDE` 30분과 임의 추가 축소 금지
4. 무릎 MILD/MODERATE의 충돌 제외·검수 대체
5. 무릎 SEVERE의 계획 없는 `REST`
6. 중대한 이상 반응의 계획 없는 `STOP_AND_SEEK_HELP`
7. 웨어러블 미연동·권한 거부의 수동 폴백
8. 필수 agent 실패의 fail-closed 결과
9. 안전 veto 우회 차단
10. 같은 입력·버전의 같은 후보와 action
11. 블록 체크 기반 `COMPLETED/PARTIAL/NOT_COMPLETED`
12. 타이머·추가 활동·캘린더 결과의 공식 상태 비변경
13. 7일 또는 3회 미수행 복귀 모드
14. 닫힌 주 리포트 확인 전 다음 계획 확정 차단
15. 동의 철회·계정 삭제·보유기간·민감정보 로그 검사

테스트를 실행하지 않았거나 필수 테스트가 실패하면 완료로 보고하지 않는다.

## 11. 남은 작업 우선순위

1. `DEFERRED` 웨어러블 범위를 provider·동의·token vault·요약 저장 단위의 별도 task로 재정의
2. PR #96에서 보류한 캘린더를 재개할지 결정하고, 재개 시 공개 route·credential vault·실 provider·통합 테스트를 별도 task로 작성
3. Google·Kakao·Naver social exchange의 실제 출시 범위와 credential owner를 확정
4. 칼로리 산식 또는 해당 필드의 MVP 제외 여부를 계약과 함께 결정
5. staging/production 삭제·보존·migration·보안·성능 리허설 수행
6. 447개 세부 요구사항과 테스트의 자동 추적 검사를 CI에 추가

각 항목은 착수 전에 `docs/tasks/TEMPLATE.md` 기반 task 문서를 만들고 실제 인수 조건, owner,
API·DB 영향, 테스트 계획을 채운다. task 문서가 없으면 구현을 시작하지 않는다.

LLM, 실제 웨어러블 연결, 실제 소셜 provider가 없어도 adapter stub과 합성 데이터로 핵심 결정·세션·주간 흐름을 검증할 수 있어야 한다.
