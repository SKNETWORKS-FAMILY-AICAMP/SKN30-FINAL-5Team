현재 준비 상태는 다음과 같다.

- 요구사항·MVP·도메인·API·데이터·아키텍처 문서는 최신 기준으로 정리되어 있다.
- `feat/backend-development-readiness`에 실행 가능한 FastAPI 공통 기반, SQLAlchemy 연결 경계, 빈 Alembic baseline, 테스트와 CI가 구현되어 있다. 기능 모듈 개발은 아직 시작하지 않았다.
- 1차 외부 데이터 수집은 56개 운동 후보, 안전 규칙 354개, 대체 관계 238개, 골든 시나리오 11건까지 완료됐다.
- 데이터 산출물은 `AGENT_ONLY`, `production_eligible=false`다. 개발·스키마 검증용 DRAFT로는 사용할 수 있지만 사용자 추천용 seed로 승격할 수 없다.
- 공통 기반은 구현됐으며 PostgreSQL migration 왕복은 CI에서 최종 확인한다. 안전 수치, 프로덕션 seed, 외부 provider 세부사항, 에이전트 상세 JSON 계약이 필요한 기능은 각 승인 게이트를 통과한 뒤 구현한다.

## 2. 기존 문서에서 바로잡은 핵심 기준

| 항목 | 최신 구현 기준 |
|---|---|
| 이용 연령 | `date_of_birth`를 필수로 받아 암호화 저장하고 사용자 timezone의 로컬 날짜로 만 14세 이상을 서버에서 검증한다. 만 나이는 저장하지 않는다. |
| 생년월일 사용 제한 | 생년월일과 만 나이는 로그·분석·LLM·에이전트·decision snapshot에 넣지 않는다. 프로필에는 서버가 일시 계산한 `age`만 표시한다. |
| 멀티에이전트 | `TrainingAgent`, `RecoveryAgent`, `SafetyAgent`, `FeasibilityAgent` 네 proposal을 공통 입력·기본 후보로 병렬 실행하고 `Coordinator`가 최종 루틴 한 개를 결정한다. |
| 안전 흐름 | 별도 `SafetyPrecheck`나 독립 `FinalSafetyGate`를 두지 않는다. `SafetyAgent`의 `PASS/NEEDS_INPUT/REVISE/BLOCKED` 의견과 결정적 안전 veto를 Coordinator가 반영한다. |
| 공개 선택지 | 운동 계획은 `FINAL_ROUTINE` 한 개만 공개한다. 내부 `ORIGINAL`, `lighter`, 안전 veto 후보는 공개하지 않는다. 운동 추천과 함께 별도 `REST` opt-out을 제공할 수 있다. |
| 요청 시간 | 사용자의 명시적 `USER_OVERRIDE`가 없으면 `requested_duration_minutes`를 바꾸지 않는다. 계획을 반환하면 `estimated_duration_seconds = requested_duration_minutes * 60`이어야 한다. |
| 수행 완료 | 경과 시간·웨어러블·캘린더 결과가 아니라 사용자가 명시적으로 완료한 운동 블록 상태로만 공식 세션 상태를 계산한다. |
| 웨어러블 | 요약 연동은 MVP다. 제공자 미연동·권한 거부·API 오류에도 수동 체크인과 앱 운동 블록 경로가 계속 동작해야 한다. |
| 캘린더 | 빈 시간 후보, 운동 계획 등록, 등록 일정의 수행 여부 확인은 MVP다. 캘린더 결과는 공식 수행 상태를 변경하지 않는다. |
| 수동 외부 운동 기록 | MVP에서 제외한다. 세션 안의 계획 외 추가 운동 기록과 세션 밖 수동 외부 운동 기록을 구분한다. |
| LLM | 선택적 설명 생성만 담당한다. 계획·시간·안전·후보 선택을 변경할 수 없고 실패 시 같은 결정과 검수 템플릿을 반환한다. |
| 데이터 승인 | 파이프라인의 `DOMAIN_APPROVED` 표기는 생성기 호환 상태일 뿐 전문가 운영 승인이 아니다. `production_eligible=false`이면 사용자 계획에 사용할 수 없다. |
| 주간 폐쇄 루프 | 닫힌 주 리포트를 요청 시 생성하고 사용자의 명시적 acknowledgement 전에는 다음 주 계획을 최종 확정하지 않는다. 콜드스타트 첫 주만 예외다. |

## 3. 시스템과 모듈 경계

백엔드는 Python 3.12+, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 기반 모듈형 모놀리스다. API 요청 안에서 결정 파이프라인을 동기 실행하며 Redis, Celery, Kafka, LangGraph, 벡터 DB, 에이전트별 마이크로서비스는 기본 구성에 넣지 않는다.

| 모듈 | 백엔드 책임 | 금지 사항 |
|---|---|---|
| `core` | 설정 검증, 공통 오류, 요청 ID, 민감정보 제거 로깅 | 비즈니스·안전 규칙 |
| `identity` | Firebase ID Token 검증 결과와 내부 사용자 연결, 소셜 adapter, 삭제 대기 접근 차단 | provider token의 도메인 DB 저장 |
| `profiles` | 온보딩, 생년월일 적격성, 장비·주의 부위·선호, 동의 현재 상태와 이력 | 나이 파생값 저장, 의료 상태 추론 |
| `catalog` | 검수 상태·출처·라이선스가 있는 운동, 대체 관계, 안전 규칙 조회 | 미승인 seed의 사용자 추천 사용 |
| `routines` | 콜드스타트·기본·주간 루틴과 불변 버전 관리 | route 안의 루틴 생성 규칙 |
| `checkins` | 사용자 직접 입력 당일 컨텍스트의 생성·교체·버전 관리 | 누락값으로 건강 상태 추정 |
| `decisions` | 입력 snapshot, 공통 후보, 네 proposal, Coordinator, 안전 의견 반영, 원자적 저장 | 자유 형식 운동 생성, 독립 final safety gate 추가 |
| `workouts` | option 선택, 세션, 블록 상태, 타이머 이력, 안전 이벤트, 종료·미수행·피드백 | 시간·웨어러블 기반 공식 완료 |
| `weekly_reports` | 월–일 경계, 논리적 마감, 리포트, acknowledgement, 다음 계획 게이트 | 열린 주의 최종 리포트 생성 |
| `integrations` | Firebase, Google/Kakao/Naver, 웨어러블, 캘린더, 선택적 LLM adapter | 외부 SDK 타입을 domain에 노출 |
| `db` | SQLAlchemy 모델, repository, transaction 지원, Alembic | repository 안의 도메인 결정 |

의존 방향은 `api -> application service -> domain -> port`다. repository와 integration은 port를 구현하며 domain은 FastAPI, ORM, Firebase SDK, LLM SDK를 import하지 않는다.

## 4. 핵심 MVP 백엔드 기능

| 기능 영역 | 구현 범위 | 핵심 불변조건·오류 처리 |
|---|---|---|
| 공통 API | `/api/v1`, Pydantic, UUID, timezone-aware ISO 8601, local date, 영문 머신 코드, 공통 오류 envelope | mutation `Idempotency-Key`, 필요한 수정의 `If-Match`, 민감 오류 상세 미노출 |
| 상태 확인 | liveness, DB·필수 설정 readiness | 인증 없이 호출하되 DB 주소·secret·stack 미노출 |
| 인증·identity | Firebase ID Token, Google, Kakao/Naver code exchange, 내부 UUID 연결 | Firebase UID를 body로 받지 않으며 토큰·이메일·전체 이름 로그 금지 |
| 온보딩·동의 | 생년월일 적격성, 프로필·장비·주의 부위·선호, 분리 동의 | 동의 현재 상태와 append-only event를 한 트랜잭션으로 저장 |
| 계정 삭제 | 즉시 접근 차단, 외부 연동 중지, 운영 DB 7일, 백업 30일 | 재식별 가능한 decision·proposal·feedback 기본 보존 금지 |
| 카탈로그 | 운동·부위·장비·장소·목표·시간·자세 콘텐츠, 출처·라이선스·검수 이력 | 실제 추천은 외부 검수와 운영 승격을 마친 `DOMAIN_APPROVED`만 사용 |
| 루틴·콜드스타트 | 검수 seed 기반 첫 주 목표·루틴, 특정 요일 비강제, 불변 루틴 버전 | 이전 리포트가 없는 최초 가입자만 주간 게이트 예외 |
| 체크인 | 피로, 요청 시간·출처, 장소, 복수 불편, 이상 반응, 선택 수면·공복·수분 | 오래된 `context_version`은 `409 STALE_CONTEXT` |
| 외부 연동 | 웨어러블 연결·동기화·일별 요약, 캘린더 빈 시간·등록·수행 여부 | 동의·권한 없이는 실행 금지, 실패해도 핵심 수동 경로 유지 |
| 결정 파이프라인 | 공통 입력·기본 후보, 네 proposal 병렬 실행, Coordinator, 결정 저장 | 필수 agent·규칙·저장 실패 시 `FAILED`, 계획 성공 응답 금지 |
| 시간·다운시프트 | 준비·운동·휴식·전환·마무리를 합산한 정확한 계획 시간, CORE 보존 | 사용자 동의 없는 시간 축소 금지, 불필요한 운동으로 시간 채우기 금지 |
| 안전 | 부위 충돌 제외, 검수 대체, REST, STOP, 복귀 상한, SafetyAgent 의견 | 안전 veto 우회 금지, 안전 후보 없으면 계획 없는 REST |
| 선택·세션 | `FINAL_ROUTINE` 또는 허용된 REST 선택, 세션 생성·시작 | REST·STOP에는 workout session을 만들지 않음 |
| 운동 실행 | 블록 `PENDING/COMPLETED`, 되돌리기, 타이머 event, 추가 활동, 안전 event | 종료된 세션의 블록 수정 금지, 타이머 event는 상태 변경 금지 |
| 종료·피드백 | COMPLETED/PARTIAL/NOT_COMPLETED/STOPPED_FOR_SAFETY, 난이도·불편·미수행 이유 | 미수행은 벌점이 아니며 가장 큰 이유 하나만 저장 |
| 복귀 | 마지막 완료 후 14일 | 요청 시간은 유지하고 외부 검수된 부하·볼륨 상한만 적용 |
| 주간 리포트 | 닫힌 주 불변 집계, 요청 시 멱등 생성, 명시적 acknowledgement | 미확인 리포트가 있으면 다음 계획 `finalized=true` 금지 |
| 다음 계획 | `INITIAL`, Coordinator 기반 `AI` 최대 2회, `USER` 직접 편집 | `NEEDS_INPUT/BLOCKED/FAILED`는 routine과 finalized 값이 모두 없음 |
| 칼로리 추정 | 앱 계획·세션에서 체중이 있을 때만 버전 산식으로 추정 | 체중 없으면 `null`, 진단·안전 판단의 단독 근거 금지 |
| 관측·보존 | 요청 ID, 마스킹 오류, latency, 구조화 failure code, 보존 작업 | 원시 체크인·웨어러블·식별자 로그 금지, 계약별 보유기간 적용 |

## 5. 결정 파이프라인과 실패 계약

```text
정규화된 최소 입력 snapshot + 검수된 공통 기본 후보
  ├─ TrainingAgent
  ├─ RecoveryAgent
  ├─ SafetyAgent
  └─ FeasibilityAgent
          ↓ 병렬 proposal 4개
결정적 Coordinator
          ↓
후보·proposal·Safety 의견·최종 결정 원자적 저장
          ↓
검수 템플릿 또는 선택적 LLM 설명
```

- 네 proposal 중 하나라도 누락되거나 `FAILED`이면 decision run 전체가 `FAILED`다.
- `SafetyAgent`의 `BLOCKED`와 결정적 안전 veto는 다른 proposal이나 Coordinator가 완화할 수 없다.
- 독립적인 최종 Safety 재검사 단계와 결과는 실행·저장·공개하지 않는다.
- proposal 상세 JSON과 공개 요약 필드는 잠정 계약이다. 증상 사용자 시나리오 검증 결과와 승인된 계약 없이 임의 확장하지 않는다.
- 성공 응답 전에 입력 snapshot, 후보, 네 proposal, Safety 의견, 최종 결과가 재현 가능하게 저장돼야 한다.

| 안전 상태 | API 결과 | 계획 |
|---|---|---|
| `PASS` | 정상 `DecisionResponse` | 최종 추천 계획 1개 |
| `REVISE` | 정상 `DecisionResponse` | 안전 조정이 반영된 계획 1개 |
| `BLOCKED` | 정상 `DecisionResponse` | `REST` 또는 `STOP_AND_SEEK_HELP`, 계획 없음 |
| `NEEDS_INPUT` | `422 NEEDS_INPUT` | 없음 |
| `FAILED` | `500/503 DECISION_FAILED` | 없음 |

## 7. 영속화와 트랜잭션 경계

- PostgreSQL이 단일 진실 공급원이다.
- DB 접근은 repository, use case와 transaction은 application service가 소유한다.
- 스키마 변경은 [`docs/DATA_MODEL.md`](../docs/DATA_MODEL.md) 갱신, Alembic migration, rollback 또는 forward-fix 설명과 함께 진행한다.
- 주요 관계·검색·제약 필드는 typed column으로 두고 JSONB는 input snapshot, proposal, 확장 metadata에 제한한다.
- `decision_runs`, `agent_proposals`, `plan_candidates`, `safety_reviews`, `decision_options`, `decision_selections`를 분리한다.
- 동의 현재 상태 갱신과 동의 event append는 한 트랜잭션이다.
- decision 기록 저장 실패, 리포트 집계 저장 실패, 다음 계획 게이트 실패는 성공 응답으로 바꾸지 않는다.
- 결정 재현에는 input schema, routine, catalog, policy, safety rules, duration rules, graph, coordinator version을 저장한다. LLM을 사용한 경우에만 model·prompt version을 저장한다.

## 12. 개발 착수 게이트

| 영역 | 현재 판단 | 착수 조건 |
|---|---|---|
| 공통 기반·health·error·request ID | 구현 완료 | `TASK-BACKEND-001`, API test와 CI 구성 완료 |
| DB baseline·repository 골격 | baseline 구현 완료 | 실제 PostgreSQL 왕복은 CI 통과 필요; 제품 테이블은 기능별 승인 필요 |
| 인증·프로필·동의 | 조건부 가능 | 생년월일 암호화 port와 test key 전략, Firebase stub 계약 |
| 카탈로그 importer | 개발용 착수 가능 | DRAFT와 production 승격을 코드·설정으로 분리 |
| 프로덕션 추천 seed | 차단 | 외부 도메인 검수와 `production_eligible=true` 승격 증적 |
| 시간·안전·복귀 엔진 | 일부 차단 | 미확정 수면·부하·복귀 상한과 부위별 규칙 승인 |
| 네 agent·Coordinator | 인터페이스 착수 가능 | 잠정 필드는 격리하고 증상 시나리오 기반 상세 계약 승인 |
| 운동 실행·주간 게이트 | 계약 기반 착수 가능 | 선행 DB·service port와 API example 확정 |
| 실제 소셜·웨어러블·캘린더 | 차단 | provider, 앱 등록, redirect, secret owner, 품질·라이선스 확정 |

개발팀장이 착수 전에 확정하거나 담당자·기한이 있는 별도 task로 분리해야 하는 항목:

- production Python patch와 PostgreSQL minor 지원 범위. 개발·CI 기준은 Python 3.12와 PostgreSQL 16으로 확정
- 공통 목표·경험·장비·장소·운동 유형·미수행 이유 코드
- 생년월일 암호화 키 관리와 접근 제한
- 수면 부족·최근 부하·복귀 첫 세션 상한
- requested duration 지원 범위와 구성 불가 시 `NEEDS_INPUT/BLOCKED` 기준
- 외부 검수자와 production seed 승격 증적
- Google/Kakao/Naver, 웨어러블, 캘린더 provider와 secret owner
- staging·production 분리, 배포 환경, SLO, 관측성 공급자
- 기존 `adult_confirmed`·`age_band_code` 호환 전략
- 공개 agent summary 상세 필드와 증상 사용자 검증 결과

미확정 항목을 임의 기본값으로 구현하거나 낮은 우선순위 문서에서 확정 계약처럼 선언하지 않는다.
