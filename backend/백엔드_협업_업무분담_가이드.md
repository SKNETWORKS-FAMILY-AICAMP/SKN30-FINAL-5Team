# 백엔드 협업 및 업무 분담 가이드

## 1. 문서 목적

이 문서는 본격적인 백엔드 구현 전에 개발팀장과 백엔드 담당자의 책임, 선행 게이트, 인계물, 첫 작업 순서와 리뷰 기준을 고정한다.

목표는 다음과 같다.

- 한 이슈에 한 명의 primary owner를 둔다.
- API·DB·도메인 규칙·데이터 파이프라인의 소유권을 섞지 않는다.
- 계약과 fixture를 먼저 인계해 프론트엔드·백엔드·데이터 작업을 병렬화한다.
- 안전·개인정보·결정 재현성 변경을 개발팀장 승인 없이 확장하지 않는다.
- 작은 PR과 실제 테스트 결과로 `develop`에 순차 통합한다.

이 문서는 업무 분담과 착수 순서를 설명하는 하위 가이드다. 제품·도메인·API·DB의 최종 계약은 상위 문서를 따른다.

## 3. 현재 착수 준비 상태

| 항목 | 상태 | 판단 |
|---|---|---|
| 요구사항·MVP·도메인·API·DB 문서 | 정리 완료 | 구현의 상위 계약으로 사용 가능 |
| 백엔드 실행 코드 | 미착수 | 모듈 README와 디렉터리 골격만 존재 |
| Python 정적 검사 | 데이터 범위 구성 | root `pyproject.toml`의 ruff·mypy 범위를 backend로 확장해야 함 |
| Python package manager | 미확정 | 기반 PR에서 한 번 결정하고 문서·lock·CI를 함께 갱신 |
| 운동 데이터 1차 수집 | 완료 | 56개 후보, 안전 규칙 354개, 대체 관계 238개, 골든 11개 |
| 운동 데이터 운영 승인 | 미완료 | `AGENT_ONLY`, `production_eligible=false`; 사용자 추천 금지 |
| 에이전트 상위 구조 | 확정 | Training·Recovery·Safety·Feasibility 병렬 proposal + Coordinator |
| 에이전트 상세 JSON·공개 요약 | 잠정 | 증상 사용자 시나리오 검증 후 확정 |
| 실제 외부 provider | 미확정 | 앱 등록·redirect·secret owner·지원 provider 필요 |
| 안전 수치·복귀 상한 | 일부 미확정 | 임의 기본값 구현 금지 |

따라서 공통 기반·테스트 골격·DB baseline 준비는 시작할 수 있다. 프로덕션 추천 seed, 미확정 안전 수치, 실제 provider 연결은 승인 task 없이는 시작하지 않는다.

## 4. 소유권 원칙

소유권은 단독 수정 권한이 아니라 primary implementation·review 책임이다. 공용 API, DB, 안전, 개인정보 계약은 지정 소유자가 혼자 확정할 수 없다.

### 4.1 개발팀장 책임

- 문서 우선순위와 아키텍처 경계 유지
- 작업을 한 issue·한 owner·한 branch·한 worktree 단위로 분리
- 공통 머신 코드와 공개 계약 변경 승인 조정
- `backend/app/domain/agents/**`, `backend/app/domain/rules/**`의 primary review
- 네 proposal·Coordinator 역할, 실패, 재현성 계약
- 요청 시간 보존, 안전 veto, 복귀 정책 불변식
- 데이터 파이프라인과 운영 seed 승격 게이트
- 외부 도메인 검수·PM·백엔드 승인 증적 연결
- production dependency, 배포, secret, migration 운영 정책 검토
- 첫 수직 슬라이스와 주간 폐쇄 루프 통합 책임

개발팀장은 백엔드 담당자의 API·DB 구현을 대신 소유하지 않는다. 계약과 안전 경계를 제공하고 교차 모듈 위험을 해소한다.

### 4.2 백엔드 담당자 책임

- `backend/app/api/**`, `backend/app/modules/**`, `backend/app/core/**`
- `backend/app/db/**`, `backend/migrations/**`
- Firebase·소셜·웨어러블·캘린더 등 `backend/app/integrations/**`
- FastAPI route, Pydantic schema, application service
- SQLAlchemy model, repository, transaction, idempotency
- 공통 오류, 요청 ID, 민감정보 제거 로깅, health
- OpenAPI example과 프론트 계약 인계
- backend unit, API, repository, integration test
- migration 적용·rollback 또는 forward-fix 검증

DB schema 변경은 백엔드가 primary owner지만 [`docs/DATA_MODEL.md`](../docs/DATA_MODEL.md)와 migration을 함께 바꾸고 개발팀장 검토를 받는다.

### 4.3 프론트엔드 책임

- OpenAPI·예제 기반 client와 mock
- 로딩·빈 상태·오류·권한 거부·안전 중단 UI
- 0초 경과 타이머, 마스코트, 운동 블록과 완료 제스처
- API 계약 변경의 영향 검토와 호환성 확인

프론트엔드는 안전·완료·다운시프트 규칙을 복제하지 않는다.

### 4.4 PM·외부 검수 책임

- 요구사항 ID와 인수 조건
- 사용자 문구와 주간 acknowledgement UX
- 출처·라이선스·운영 범위 검토
- 안전·통증·복귀 콘텐츠의 외부 도메인 승인 증적
- 개인정보·보유·삭제 정책의 출시 전 검토 조정

| 경로·계약 | Primary | 필수 검토·협업 |

| `data/**` | 개발팀장·백엔드/데이터 | PM, 외부 도메인 검수 |

## 7. 개발팀장이 착수 전에 닫아야 할 게이트

### 7.1 기반 PR 게이트

- 공식 backend task와 인수 조건
- `develop`에서 분기한 작업 branch와 전용 worktree
- Python package manager, 정확한 Python·PostgreSQL 버전
- backend production·dev dependency와 추가 이유
- formatter·linter·type checker·pytest 명령
- 환경 변수 이름과 secret reference 경계
- 테스트 DB와 migration 검증 방식

### 7.2 기능 계약 게이트

- 전체 목표·경험·장비·장소·운동 유형·미수행 이유 코드
- 기존 `adult_confirmed`·`age_band_code` 호환 전략
- 생년월일 암호화 키 관리와 테스트용 key 전략
- requested duration 지원 범위와 구성 실패 매핑
- 수면·누적 부하·복귀 첫 세션의 외부 검수 상한
- agent proposal·공개 summary 잠정 필드의 격리 방식

### 7.3 외부·운영 게이트

- Google/Kakao/Naver 앱 등록, redirect, state/nonce 만료, secret owner
- MVP 웨어러블·캘린더 provider와 API·품질·라이선스
- 외부 도메인 검수자와 `production_eligible=true` 승격 증적
- local/test/staging/production 분리와 배포 담당
- 관측성 공급자, SLO, 삭제·백업 만료 작업 owner

게이트를 당장 닫을 수 없으면 owner와 due date가 있는 별도 task로 분리한다. 미확정 안전값을 코드 상수로 임시 확정하지 않는다.

## 9. 첫 백엔드 작업 카드

아래 명칭은 공식 요구사항 ID를 대신하지 않는 착수 카드다. 실제 작업 전 [`docs/tasks/TEMPLATE.md`](../docs/tasks/TEMPLATE.md)로 issue 문서를 만들고 요구사항·AC·TC ID를 연결한다.

### 카드 A — backend 기반 결정

- Primary: 개발팀장
- 목표: package manager, runtime, PostgreSQL, backend 도구·CI 명령을 한 번 결정
- 변경 예상: root Python 설정·lock, backend package, local development, CI 관련 파일
- 완료 기준: 새 환경에서 의존성 설치, lint/type/test 명령 재현, production dependency 이유 기록
- API·DB 영향: 없음

### 카드 B — FastAPI 공통 기반

- Primary: 백엔드
- 선행: 카드 A
- 포함: app factory, `/api/v1` router, live/ready, 공통 오류, `X-Request-ID`, 마스킹 로그, API test fixture
- 제외: auth, business rule, agent, catalog seed, 외부 provider
- 인수 조건:
  - live는 프로세스 생존만 확인한다.
  - ready는 DB·필수 설정 상태를 확인하되 연결 문자열·secret·stack을 노출하지 않는다.
  - 모든 오류는 공통 envelope와 request ID를 가진다.
  - 토큰·이메일·전체 이름·체크인 원문이 로그에 남지 않는다.

### 카드 C — PostgreSQL·Alembic baseline

- Primary: 백엔드
- 선행: 카드 A
- 포함: engine/session 경계, metadata, 첫 baseline, migration test DB
- 제외: 모든 논리 테이블을 한 번에 완성하는 작업
- 인수 조건:
  - 앱 시작과 테스트에서 설정이 검증된다.
  - migration forward와 rollback 또는 문서화한 forward-fix를 검증한다.
  - domain은 SQLAlchemy model에 의존하지 않는다.

### 카드 D — 인증·연령·동의 수직 조각

- Primary: 백엔드
- 선행: 카드 B·C, 암호화·호환 전략

## 13. 코딩·리뷰 규칙

- route는 인증 컨텍스트·schema 검증·HTTP 변환 후 application service에 위임한다.
- service가 use case, transaction, idempotency를 관리한다.
- business rule은 domain에 두고 route·repository에 복제하지 않는다.
- repository는 DB 접근만 캡슐화한다.
- 외부 provider는 integration adapter 뒤에 둔다.
- domain은 FastAPI, ORM, Firebase SDK, LLM SDK를 import하지 않는다.
- 공개 API 변경은 API 계약, example, frontend mock/client, compatibility test를 함께 갱신한다.
- DB 변경은 DATA_MODEL, Alembic migration, rollback 또는 forward-fix를 함께 갱신한다.
- 안전 규칙 변경은 policy/ruleset version, 골든 테스트, 개발팀장·PM·외부 검수 증적이 필요하다.
- 생성 파일을 수동 편집하지 않는다.
- 다른 기여자의 미커밋 작업을 덮어쓰지 않는다.
- `main`·`develop`에 직접 커밋하거나 공유 branch에 force push하지 않는다.

우선 리뷰 대상:

- API response breaking change
- migration 없는 schema 변경
- 임의 안전 임계값 또는 LLM-only 안전 판단
- 독립 final safety gate의 무승인 재도입
- 필수 agent 실패인데 계획을 성공 반환하는 경로
- 생년월일·토큰·이메일·이름·원시 건강 데이터 로그
- decision proposal과 final 결과를 덮어쓰는 저장 구조
- 경과 시간·웨어러블·캘린더 기반 공식 완료
- 사용자 동의 없는 requested duration 축소
- `production_eligible=false` seed의 사용자 추천
- business rule이 포함된 route·repository
- business rule 변경에 대한 테스트 누락

## 14. 코딩 에이전트 사용 규칙

코딩 에이전트도 동일한 소유권·계약·개인정보 규칙을 따른다. 넓은 기능 전체가 아니라 독립적으로 검증 가능한 한 task만 맡긴다.

프롬프트에는 최소한 다음을 포함한다.

- 수정 허용·금지 경로
- 사용할 service·repository port
- 변경 금지 API 필드·enum·DB schema
- 상태 전이와 도메인 불변조건
- 인수 조건과 필수 테스트
- migration 필요 여부
- 개인정보 로그 금지 항목
- 안전 규칙 변경 권한 유무
- DRAFT와 production 데이터 사용 경계

에이전트의 완료 보고만으로 병합하지 않는다. primary owner가 diff, 테스트 출력, 계약 영향, 민감정보 노출을 직접 검토한다.

## 15. 필수 테스트

백엔드 변경 시 수정 영역에 맞는 formatter, linter, type checker, unit, API·repository·integration test를 실행한다.

규칙·agent 변경에는 다음을 추가한다.

- 정상 `KEEP`
- 요청 시간과 CORE를 보존한 `DOWNSHIFT`
- 무릎 불편 충돌 제외·검수 대체
- 웨어러블 없는 수동 체크인
- 필수 agent 실패 fail-closed
- 안전 veto 우선
- 같은 입력·버전의 재현성
- LLM 실패의 동일 결정·템플릿 폴백

workout·weekly 변경에는 다음을 추가한다.

- 블록 체크 기반 `COMPLETED/PARTIAL/NOT_COMPLETED`
- 중복 mutation의 한 번 반영
- 종료 세션 item 수정 차단
- timer·추가 운동·캘린더 결과의 공식 상태 비변경
- 열린 주 report 거부
- report acknowledgement 전 다음 계획 finalize 차단

실행하지 않은 테스트를 통과로 보고하지 않으며 필수 테스트 실패 시 완료로 선언하지 않는다.

## 17. 즉시 공유·중단 조건

다음 상황에서는 임의로 진행하지 않고 개발팀장에게 공유한다.

- 상위 문서끼리 충돌함
- 공개 API 필드 삭제·이름 변경이 필요함
- 승인되지 않은 DB 관계·migration이 필요함
- 새로운 안전 임계값·통증 처리·복귀 상한이 필요함
- 독립 Safety 사전·최종 게이트를 추가해야 할 것처럼 보임
- 승인되지 않은 운동·대체 관계·회복 콘텐츠가 필요함
- `production_eligible=false` 데이터를 사용자 계획에 사용해야 할 것처럼 보임
- provider token·생년월일·건강 데이터 저장 범위를 넓혀야 함
- transaction이 여러 모듈의 repository를 직접 조작해야 함
- decision 성공 전에 일부 기록만 저장됨
- 기존 미커밋 변경과 범위가 겹침
- 새 production dependency, worker, queue, object storage가 필요함
- package/runtime/provider/배포 결정이 상위 문서와 달라짐

협업의 우선순위는 빠른 코드 생성보다 계약 호환성, 안전, 재현성, 개인정보 보호다.
