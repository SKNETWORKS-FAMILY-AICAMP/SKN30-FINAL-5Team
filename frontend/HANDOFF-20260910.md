# 백엔드 인계: 운동 세션 중단·피드백·주간 마감 · 2026-09-10

## 최신 develop 반영 후 결론

현재 작업 브랜치에는 `origin/develop`의 `ac09c62`까지 병합되어 있다. 아래 내용은 해당 코드와 API 계약, 데이터 모델, 관련 테스트를 다시 대조한 결과다.

기존에 가장 크게 우려했던 **일반 중단 후 피드백 409**, **동일 세션 피드백 재제출 409**, **중단 사유 미저장**, **종료되지 않은 일반 중단 세션 자체가 주간 리포트를 막는 문제**는 최신 develop에서 해결됐다. 이 네 항목은 추가 인계 대상이 아니다.

다만 안전 중단의 주간 집계, 사용자 timezone 기준 재개 판정, 세션 상세 read 계약, 앱 강제 종료로 사유가 전혀 남지 않은 세션, 피드백 갱신 응답 시각에는 아직 백엔드 확인·수정이 필요하다.

## develop에서 해결된 항목 · 인계 제외

### 1. 일반 중단 후 피드백 409 · 해결됨

기존 문제 예시:

```text
사용자가 운동 블록 10개 중 3개를 완료함
→ "시간이 부족해요"를 선택하고 일반 중단
→ 앱이 "오늘 안에 홈에서 이어할 수 있어요"와 피드백 화면을 표시
→ 사용자가 "어려웠어요 / 운동량이 많았어요"를 선택하고 저장
→ 서버가 409 INVALID_STATE_TRANSITION 반환
→ 완료한 3개 블록과 중단 사유는 남지만 난이도 피드백은 DB에 저장되지 않음
→ 현재 프론트 규칙상 저장이 성공해야 홈으로 갈 수 있어 피드백 화면에 계속 머무름
```

최신 develop의 실제 동작:

```text
운동 블록 3/10 완료
→ PATCH /stop
→ execution_state_code=STOPPED_RESUMABLE
→ status_code=IN_PROGRESS와 is_resumable=true 유지
→ POST /feedback
→ 성공, session_status_code=IN_PROGRESS
→ 피드백을 저장해도 당일 이어하기 가능
```

`record_feedback`이 종료 상태뿐 아니라 `STOPPED_RESUMABLE`도 허용하고, 수행 중인 `RUNNING`, `RESTING`, `PAUSED`는 계속 거부한다. 응답 스키마도 `IN_PROGRESS`를 허용한다. 해당 조합의 단위 테스트가 추가되어 있다.

### 2. 재개 후 최종 피드백 갱신 · 해결됨

예시:

```text
일반 중단 시 HARD + VOLUME_HIGH 저장
→ 당일 재개
→ 운동 추가 수행 또는 완료
→ 최종 화면에서 APPROPRIATE 제출
→ canonical 최종값은 APPROPRIATE 하나
→ 이전 VOLUME_HIGH row는 삭제
```

최신 develop은 `workout_feedback`의 세션당 한 행을 upsert하고 자식 행도 마지막 요청 값으로 전부 교체한다. `409 FEEDBACK_ALREADY_EXISTS`는 더 이상 정상 흐름에서 발생하지 않는다. DB의 `created_at`은 최초 저장 시각을 유지하고 `updated_at`은 마지막 답변 시각으로 갱신되며 migration `0054_workout_feedback_updated_at`이 추가됐다.

### 3. 일반 중단 사유와 주간 리포트 · 해결됨

기존 문제 예시:

```text
화요일에 3/10 블록 완료
→ 일반 중단 후 홈 이동
→ 그날 다시 재개하지 않음
→ 다음 월요일에도 세션 row는 IN_PROGRESS
→ 예전 구현에서는 주간 리포트가 WEEK_OUTCOMES_INCOMPLETE로 막힘
```

최신 develop에서는 `/stop` 요청의 `not_completed_reason_code`를 `workout_skip_feedback`에 저장하고, 다시 중단하면 마지막 사유로 교체한다. 닫힌 주의 리포트는 세션 row가 `IN_PROGRESS`라는 이유만으로 거부하지 않고 완료 블록 수로 `PARTIAL` 또는 `NOT_COMPLETED`를 계산한다.

따라서 **정상적으로 중단 사유를 고른 흐름에는 자정 scheduler나 세션 강제 종료가 필요하지 않다.** `STOPPED_RESUMABLE`은 DB에서 열린 채로 있어도 닫힌 주의 리포트 계산 대상이 된다.

## 남은 백엔드 인계 사항

### 1. 우선순위 높음: 안전 중단 세션이 주간 리포트를 409로 막을 수 있음

사용자 예시:

```text
수요일에 운동 블록 10개 중 2개 완료
→ "통증·이상 반응"으로 안전 중단
→ 세션은 STOPPED_FOR_SAFETY로 정상 저장
→ 다음 주 주간 리포트 생성
→ 집계 코드는 Safety Event를 안전 중단으로 인식하지 못함
→ 블록만 보고 PARTIAL로 다시 계산
→ 저장 상태 STOPPED_FOR_SAFETY와 PARTIAL이 다르다고 판단
→ 409 WEEK_OUTCOME_INCONSISTENT
→ 리포트 확인과 다음 주 계획 확정까지 막힐 수 있음
```

확인된 원인은 현재 신규 Safety Event가 `result_code=SESSION_STOPPED`를 저장하면서 `resulting_action_code=NULL`로 저장되지만, 주간 evidence 조회는 `resulting_action_code IN (REST, STOP_AND_SEEK_HELP)`만 보고 `safety_stopped`를 계산한다는 점이다.

또한 최신 문서는 공식 수행 상태를 완료 블록 기반 `COMPLETED/PARTIAL/NOT_COMPLETED` 축과 안전 중단 여부 축으로 분리한다고 설명하지만, 현재 도메인 계산기는 `safety_stopped=true`이면 공식 상태 자체를 `STOPPED_FOR_SAFETY`로 바꾼다. 단순히 조회 조건 한 줄만 고치지 말고 두 축의 계약을 함께 정합화해야 한다.

필수 확인·수정 조건:

- 신규 Safety Event의 canonical 값인 `result_code` 또는 세션의 `execution_state_code=STOPPED_SAFETY`로 안전 중단 여부를 판정한다.
- 완료 상태는 블록으로 계산하고, 안전 중단 횟수는 별도 지표로 계산한다는 최신 계약과 서비스 구현을 일치시킨다.
- 안전 중단 0블록 세션에 일반 미수행 사유를 추가로 요구할지, Safety Event 자체를 충분한 사유로 볼지 명시한다.
- 실제 PostgreSQL/API 흐름으로 `안전 중단 → 주 마감 → 리포트 생성 → acknowledgement → 다음 주 plan finalize`를 검증한다.

### 2. 우선순위 높음: 자정 이후 같은 한국 날짜의 이어하기가 거부될 수 있음

사용자 예시:

```text
프로필 timezone: Asia/Seoul
9월 10일 00:30에 운동을 일반 중단
→ 앱은 occurred_at="2026-09-09T15:30:00.000Z" 전송
→ 세션 local_date는 2026-09-10
→ 서버는 UTC 문자열의 date인 2026-09-09와 직접 비교
→ 같은 사용자 날짜인데도 409 INVALID_STATE_TRANSITION
```

`RESUME` 처리에서 현재 `request.occurred_at.date()`와 `state.local_date`를 직접 비교한다. React Native의 `new Date().toISOString()`은 UTC 문자열이므로 Asia/Seoul 기준 00:00~08:59에는 날짜가 하루 전으로 보인다.

필수 수정 조건:

- 사용자의 저장된 IANA timezone으로 `occurred_at`을 변환한 뒤 local date를 비교한다.
- 요청 문자열에 포함된 offset을 사용자 timezone 대신 신뢰해 날짜를 결정하지 않는다.
- `Asia/Seoul 00:00~08:59 같은 local date 재개 성공`, `다음 local date 재개 거부` 경계 테스트를 추가한다.

### 3. 우선순위 중간: 세션 상세 응답만으로 실행 상태와 타이머를 복원할 수 없음

사용자 예시:

```text
운동 3/10 진행 후 "나중에 이어하기"로 중단
→ 앱을 완전히 종료하고 다시 실행
→ GET /workout-sessions/{id} 응답은 status_code=IN_PROGRESS만 반환
→ 앱은 RUNNING인지 STOPPED_RESUMABLE인지 구분할 수 없음
→ "진행 중"과 "이어하기" 문구, 재개 가능 여부, 누적 타이머를 정확히 복원할 수 없음
```

세션 상세 응답에는 현재 `completed_plan_item_ids`와 `current_plan_item_id`가 이미 존재한다. 그러나 다음 실행 상태 필드는 아직 없다.

- `execution_state_code`
- `is_resumable`
- `stop_reason_code`
- `accumulated_progress_seconds`
- `accumulated_rest_seconds`
- `accumulated_paused_seconds`

이 필드를 additive로 제공하고 상세 조회와 `/home`의 세션 응답에서 동일하게 노출해야 한다. `status_code=IN_PROGRESS` 하나로 실행 상태를 추측하게 두면 안 된다.

### 4. 우선순위 중간: 앱 강제 종료로 사유가 전혀 남지 않은 0블록 세션은 여전히 주간 리포트를 막음

사용자 예시:

```text
사용자가 운동 시작 버튼을 누름
→ 아직 블록을 하나도 체크하지 않음
→ 중단 사유 화면을 거치지 않고 앱을 강제 종료하거나 휴대폰을 잃어버림
→ 세션은 IN_PROGRESS, 완료 블록 0개, 미수행 사유 없음
→ 사용자가 그 주에 다시 앱을 열지 않음
→ 다음 주 리포트 생성 시 WEEK_OUTCOMES_INCOMPLETE
→ 다음 주 계획 확정도 진행되지 못함
```

명시적으로 `/stop`을 호출한 정상 흐름은 해결됐지만, 시작 직후 앱 종료처럼 서버에 사유를 보낼 기회가 없었던 세션은 별도다. 현재 테스트도 이 경우 `WeekOutcomesIncompleteError`가 발생하는 것을 기대한다.

제품·계약 결정이 필요한 선택지:

- 주 마감 전에 재방문하면 사유 입력을 요구하고 저장한다.
- 끝내 재방문하지 않은 경우를 위한 `ABANDONED/UNKNOWN` 같은 machine code를 additive로 정의한다.
- 사유 없는 0블록 세션 하나가 주간 리포트 전체와 다음 주 계획을 막지 않도록 별도 fallback 정책을 정의한다.

사용자가 선택하지 않은 `TIME_SHORTAGE`, `FATIGUE` 등을 서버가 임의로 추정해서 저장하면 안 된다.

### 5. 우선순위 낮음: 피드백 갱신 응답의 `created_at`이 계약과 다름

사용자 예시:

```text
10:00 첫 피드백 저장
→ DB created_at=10:00, updated_at=10:00
11:00 재개 후 최종 피드백 저장
→ DB created_at=10:00, updated_at=11:00으로 정상
→ 하지만 두 번째 API 응답의 created_at은 11:00으로 반환
→ 응답만 보면 피드백이 11:00에 처음 생성된 것처럼 보임
```

API 계약은 `created_at`을 최초 저장 시각으로 정의하지만 `record_feedback`은 매 요청의 현재 시각을 응답 `created_at`에 넣는다. repository는 실제 DB `created_at`을 보존하고 있으므로 응답만 불일치한다.

필수 수정 조건:

- upsert 후 저장된 행의 `created_at`을 응답한다.
- 필요하면 `updated_at`을 optional additive 응답 필드로 추가하고 API 문서·프론트 타입을 함께 갱신한다.
- 첫 저장과 두 번째 저장의 응답 시각을 검증하는 서비스/API 테스트를 추가한다.

### 6. 우선순위 낮음: 주간 리포트 생성과 피드백 갱신의 경쟁 정책

현재 정상적인 단일 기기 화면에서는 피드백 저장 후 홈으로 이동하므로 흔한 사용자 흐름은 아니다. 다만 앱 강제 종료, 여러 기기, 응답 유실, 향후 기록 상세의 피드백 편집 기능에서는 다음 순서가 가능하다.

```text
리포트가 피드백 A를 읽고 input_hash 생성
→ 거의 동시에 같은 세션의 피드백이 B로 갱신
→ 이미 생성된 리포트에는 A가 남고 canonical feedback은 B가 됨
→ 재요청 시 REPORT_INPUT_CHANGED가 발생할 수 있음
```

리포트 생성 시 evidence snapshot과 관련 세션·피드백 갱신을 어떤 잠금 또는 cutoff 정책으로 직렬화할지 명시해야 한다. 이미 생성된 리포트를 무조건 덮어쓰는 방식은 acknowledgement와 재현성 계약을 해칠 수 있으므로 사용하지 않는다.

## 백엔드 필수 검증 시나리오

1. 일반 중단: 3/10 완료 → `/stop` → HARD+VOLUME_HIGH 저장 성공 → 세션은 계속 재개 가능.
2. 최종 갱신: 재개 → 추가 수행 또는 `/finish` → APPROPRIATE 저장 → canonical row 1개, 이전 difficulty reason 0개.
3. 상태 제한: RUNNING/RESTING/PAUSED feedback은 409, STOPPED_RESUMABLE과 종료 세션은 성공.
4. 중단 사유: 0블록 일반 중단도 `not_completed_reason_code` 저장 → 닫힌 주 리포트에서 NOT_COMPLETED로 집계.
5. 안전 주간 집계: 안전 중단 0블록·일부 블록 각각 리포트 생성 성공, 완료 축과 안전 축이 계약대로 집계.
6. timezone: Asia/Seoul 00:30의 UTC ISO 요청으로 같은 날 재개 성공, 다음 사용자 날짜 재개 거부.
7. 상세 조회: 중단 후 앱 재시작을 가정해 실행 상태·재개 가능 여부·누적 타이머 복원.
8. 무응답 이탈: 시작 직후 앱 종료 후 주 마감에서도 정의된 fallback으로 리포트와 다음 주 finalize 진행.
9. 응답 시각: 피드백 두 번째 저장에서 최초 `created_at` 보존, `updated_at` 갱신.
10. 멱등: commit 뒤 응답 유실을 가정한 같은 키 재시도는 같은 성공 응답 반환.
11. 경쟁: 피드백 갱신과 report create 동시 요청 결과가 문서화한 snapshot 정책과 일치.
12. 권한: 다른 사용자 session ID는 존재를 노출하지 않고 404.

## 검증 근거와 한계

- 최신 develop 병합 상태에서 workout/weekly report 단위·API·repository 테스트를 실행했다: `50 passed, 2 skipped`.
- skip 2건은 `TEST_DATABASE_URL`이 없어 실행되지 않은 실제 PostgreSQL 전용 테스트다.
- 일반 중단 feedback 허용, 피드백 최종값 교체, 중단 사유 교체, 열린 세션의 블록 기반 주간 집계는 현재 자동 테스트로 확인했다.
- 안전 중단부터 실제 주간 리포트 생성까지 이어지는 PostgreSQL/API 통합 테스트는 현재 없다.
- 공개 API, DB 스키마, 운영 데이터와 배포는 이 문서 작업에서 변경하지 않았다.
- 새 건강·식별 정보의 저장, 로그, 외부 전송을 요구하지 않는다.
