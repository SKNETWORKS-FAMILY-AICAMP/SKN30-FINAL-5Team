# 백엔드 전달: 휴식 통합과 안전 중단 분리

- 작성일: 2026-09-08
- 요청자: 프로젝트 소유자
- 후속 구현 primary owner: 백엔드 담당자 지정 필요
- 관련 프론트 작업: [TASK-UI-REST-FLOW.md](TASK-UI-REST-FLOW.md)
- 상태: **최종 제품 흐름에 맞추기 위한 백엔드 정리 요청. API·DB 변경은 아직 구현하지 않음.**

## 1. 전달 요약

최종 목표는 사용자가 앞서 요청한 흐름이다. 프론트에서 `NOT_COMPLETED`의 문구만 휴식으로 바꾸는 현재 처리는 호환 단계이며, 최종 상태 코드 정리까지 완료한 것이 아니다.

**휴식하기 버튼은 의도적으로 제거했다. 휴식은 사용자가 버튼으로 선택해야 생기는 상태가 아니다. 앱 미접속, 접속했지만 루틴 미생성, 루틴 생성 후 운동 미시작, 운동 시작 후 0블록 중단은 모두 휴식이다.** 결정·루틴·운동 세션 행 또는 클라이언트 요청이 없어도 해당 날짜의 휴식 결과를 서버가 제공해야 한다. 이 네 경우의 휴식 분류는 확정된 요구사항이며, 구현 방식만 공동 설계 대상이다.

백엔드는 완료 블록 수로 수행 결과를 `COMPLETED` / `PARTIAL` / `REST`로 일관되게 제공하는 방향으로 계약을 정리해야 한다. 안전 중단 여부는 수행 결과와 별도로 보존해야 한다. **안전 중단했다는 이유만으로 이미 수행한 블록을 휴식으로 바꾸면 안 된다.**

현재 `REST`는 운동 전 결정·선택에 쓰이고, 운동 후 0블록 종료는 `NOT_COMPLETED`에 저장된다. 두 경로를 동일한 휴식 기록으로 조회·집계할 수 있어야 한다. 다만 운동 권고, 실제 수행 결과, 안전 중단 원인은 서로 다른 정보이므로 이름이 같다는 이유로 테이블이나 필드를 무조건 합치지는 않는다.

이번 전달 작업에서는 백엔드 코드·공개 계약·DB를 변경하지 않았다. 아래 목표 API 표현과 전환 방식은 프론트·백엔드·개발팀장이 함께 확정할 후속 구현안이다.

## 2. 최종 제품 흐름

| 상황 | 최종 수행 결과 | 화면과 이동 |
|---|---|---|
| 앱에 접속하지 않음 | `REST` / 휴식 | 앱 요청 없이도 날짜별 결과에 포함하고 이후 접속 시 캘린더·리포트에서 조회 |
| 앱에 접속했지만 루틴을 생성하지 않음 | `REST` / 휴식 | 결정·루틴·세션 생성이나 휴식 선택을 요구하지 않음 |
| 루틴을 생성했지만 운동을 시작하지 않음 | `REST` / 휴식 | 루틴 생성 여부를 수행으로 인정하지 않으며 세션이 없어도 집계 |
| 운동 시작 후 완료 블록 0개로 일반 중단 | `REST` / 휴식 | 중단 시트의 사유는 받고 운동 후 피드백은 받지 않는다. 종료 저장 성공 후 홈으로 이동 |
| 완료 블록이 1개 이상이고 미완료 블록이 남은 상태에서 중단 | `PARTIAL` / 부분 수행 | 피드백 화면 → 선택 후 저장 버튼 활성화 → 저장 성공 후 홈 |
| 전체 운동 블록 완료 | `COMPLETED` / 완료 | 피드백 화면 → 선택 후 저장 버튼 활성화 → 저장 성공 후 홈 |
| 완료 블록 0개로 안전 중단 | `REST` + 안전 중단 정보 | 운동 후 피드백 없이 홈으로 이동하되 안전 안내와 재개 금지 유지 |
| 일부 블록 완료 후 안전 중단 | `PARTIAL` + 안전 중단 정보 | 수행 기록을 보존하고 안전 안내 및 피드백 제공, 재개 금지 유지 |
| 과거 미수행 기록 | 휴식으로 통합 | 조회·캘린더·리포트의 사용자 명칭과 집계에 동일하게 적용 |

- 수행 결과는 명시적으로 완료한 블록으로 서버가 판정한다. 경과 시간이나 클라이언트가 보내는 임의 상태값으로 확정하지 않는다.
- 체크인 이후 자발적 휴식 버튼과 그 진입 경로는 제거한다. 기존 버튼 디자인 소스는 보존하되 화면에 마운트하지 않는다.
- 피드백 화면의 별도 `홈으로` 버튼은 제거한다. `피드백 저장하고 홈으로`는 선택 전 비활성화하고 저장 성공 후 이동한다.
- **중단 사유와 운동 후 피드백은 다른 입력이다.** 중단 사유는 왜 오늘 그만뒀는지이고, 운동 후 피드백은 난이도·피로도·통증 여부다. 0블록 종료에서 없애는 것은 **피드백**이며 사유는 계속 받는다(프로젝트 소유자 결정, 2026-09-08). 안전 중단은 Safety Event가 원인을 이미 담으므로 사유를 따로 묻지 않는다.
- `HARD` 선택 시 현재 계약의 추가 이유 선택 조건을 유지한다.
- 휴식의 달 아이콘은 캘린더와 주간 리포트에서 통일한다.
- **기록 행이 없다는 이유로 휴식을 누락하지 않는다.** 오늘의 휴식 분류는 이후 실제 운동에 따라 부분 수행·완료로 갱신할 수 있어야 한다. 휴식 표시만을 이유로 진행 중인 세션을 강제 종료하거나 운동 시작을 차단하지 않는다. 안전 중단의 재개 금지는 별도로 유지한다.
- 미래 날짜는 휴식 실적으로 미리 집계하지 않는다. 서비스 기록 시작일·사용자 timezone·일자 마감·지연 동기화 기준은 백엔드 계약에 명시한다. 이 경계 설계는 위 네 가지 휴식 사례를 제외할 근거가 아니다.

## 3. 현재 코드에서 확인한 불일치

### 3.1 운동 전 REST와 운동 후 휴식의 저장 경로가 다름

- `backend/app/modules/workouts/service.py`의 결정 선택 처리에서 `REST`는 운동 세션을 생성하지 않는다. 응답의 `workout_session`은 `null`이다.
- `backend/app/db/models/workout.py`에는 결정 선택의 `selected_action_code=REST`, 예정 운동의 `REST_SELECTED`, 세션의 `NOT_COMPLETED`가 각각 존재한다.
- `/api/v1/workout-sessions/{session_id}/finish`는 현재 0블록 종료를 거부한다.
- `/api/v1/workout-sessions/{session_id}/not-completed`는 `reason_code`를 필수로 받고 `NOT_COMPLETED`를 반환한다.
- 현재 프론트는 일반 0블록 중단에 이 기존 API를 호출한다. **프론트가 `REST` 상태 코드를 보내고 있는 것은 아니다.** 사유를 보내고 서버가 반환한 `NOT_COMPLETED`를 휴식으로 표시한다.

**부분 수행으로 중단하면 사용자가 고른 중단 사유가 버려진다.** `WorkoutScreen.tsx`의 중단 시트는 사유를 받은 뒤, 완료 블록이 0개면 `/not-completed`로 사유와 함께 보내지만 1개 이상이면 `/finish`를 호출한다. `/finish` 요청 본문에는 사유 자리가 없다. 결과적으로 `5블록 중 3블록을 하고 시간이 없어서 멈춤` 같은 가장 쓸모 있는 학습 신호가 저장되지 않는다. 0블록일 때만 사유가 남는 현재 구조는 사유 표본을 한 번 더 편향시킨다(C-4).

따라서 버튼 제거와 표시 문구 변경만으로는 REST 선택 이력과 세션 휴식 이력이 서버에서 통합되지 않는다. 원래 선택을 운동 도중 `REST`로 덮어써서 해결하면 실제 운동 기록의 출처를 훼손할 수 있다.

### 3.2 SAFETY가 휴식으로 보이는 지점

`SAFETY`라는 단일 코드로 처리되는 구조가 아니다. 실행 상태 `STOPPED_SAFETY`, 구형 세션 상태 `STOPPED_FOR_SAFETY`, Safety Event와 그 안내를 구분해서 확인해야 한다.

- 프론트 `frontend/src/features/home/calendarReportModel.ts`의 `sessionDayStatus()`는 `STOPPED_FOR_SAFETY`를 블록 수 확인 없이 `rest`로 변환했다. **이 경로에서는 일부 블록을 완료한 안전 중단도 휴식으로 보였다.** 2026-09-08 프론트에서 별도 표시로 분리했으며 상세는 3.4를 따른다.
- 반면 안전 중단 직후 응답에는 `completion_code`가 있어, `SessionResultScreen.tsx`와 `MainFlow.tsx`는 0블록이면 홈으로, 부분 수행이면 결과 화면으로 나눈다. 즉 종료 직후 화면과 이후 기록 화면의 기준이 다르다.
- 백엔드 `derive_completion_code()`는 안전 여부와 독립적으로 블록 수를 사용하지만, 같은 파일의 `derive_official_session_status()`는 안전 중단이면 `STOPPED_FOR_SAFETY`를 우선 반환한다.
- `backend/app/db/repositories/workout.py`의 `transition_execution_state()`는 신규 안전 중단 저장에서도 `status_code=STOPPED_FOR_SAFETY`를 쓴다. 과거 데이터에만 해당하는 문제가 아니며, 저장된 `completion_code=PARTIAL`과 목록의 구형 상태가 함께 존재할 수 있다.
- `backend/app/modules/weekly_reports/service.py`의 `_build_report_values()`는 후자의 구형 판정으로 집계한다. 현재 `safety_stopped_session_count`는 `stopped_for_safety`와 같은 수를 담으며, 이것만으로 수행 결과와 안전 사건 집계가 완전히 분리된 것은 아니다.
- **완료 블록이 지표에서 사라지는 경로가 있다.** 같은 파일의 `persistence_rate`는 `(completed + partial) / target`이고, 안전 중단은 `official_status`가 `STOPPED_FOR_SAFETY`라 `partial`에 들어가지 않는다. 5블록 중 3블록을 완료한 뒤 통증으로 중단하면 그 3블록이 지속률과 조정 성공률에서 0으로 취급된다. **참고 계속한 경우가 지표상 유리해지므로 안전 인센티브가 뒤집힌다.** 반면 `backend/app/db/repositories/reward.py`의 `list_reward_eligible_workouts()`는 `STOPPED_FOR_SAFETY`에 부분 수행과 같은 보상을 지급한다. 즉 같은 사건을 보상은 인정하고 주간 지표는 인정하지 않는 내부 불일치가 있다.

안전 중단 0블록의 주 결과가 휴식인 것은 최종 흐름과 맞지만, 안전 정보까지 사라지거나 안전 중단 전체가 휴식이 되는 것은 목표가 아니다.

### 3.3 조회·재접속·리포트에서도 동일한 정보가 필요함

- 현재 프론트의 `WorkoutSessionLogSummary`에는 `status_code`와 블록 개수는 있지만, 수행 결과와 안전 중단을 분리해서 소비하는 계약이 없다.
- 캘린더는 세션 목록을 중심으로 계산한다. 과거 REST 선택뿐 아니라 앱 미접속·루틴 미생성·운동 미시작으로 **세션 자체가 없는 날**을 휴식으로 읽는 서버 결과가 필요하다. 기존 세션 응답 enum만 바꿔서는 이 사례들을 해결할 수 없다.
- 0블록 안전 중단 직후 홈 안전 안내는 현재 프론트 메모리에서 유지한다. 재실행 이후에도 동일한 안전 안내와 제한을 복원하려면 조회 응답이 이를 지원해야 한다.
- 주간 집계는 현재 `NOT_COMPLETED` 기록에 사유가 없으면 `WeekOutcomesIncompleteError`를 발생시킬 수 있다. 종료 API에서 사유만 선택 사항으로 바꾸면 사유 없는 휴식의 리포트 생성이 실패할 수 있다.

### 3.4 프론트가 먼저 반영한 임시 처리 (2026-09-08)

서버 일별 결과 계약이 나오기 전까지 캘린더만 최종 흐름에 가깝게 보이도록 클라이언트에서 임시 처리했다. **여기서 쓴 규칙 자체는 최종 흐름과 같으므로 백엔드가 그대로 가져가도 된다.** 서버 계약이 확정되면 클라이언트 계산은 제거하고 서버 결과를 소비한다.

계약을 맞출 때 지킬 제약은 두 가지다.

1. **판정은 서버가 소유한다.** 규칙이 달라서가 아니라, 클라이언트 계산은 기기 timezone·앱 버전에 따라 흔들려 과거 리포트 숫자가 나중에 바뀔 수 있기 때문이다. 같은 규칙을 서버가 확정해 재현 가능하게 만든다.
2. **표시 칸을 나누더라도 지표에서 완료 블록을 잃지 않는다.** 상세는 A-5를 따른다.

아래 두 가지는 클라이언트가 알 수 없어 임시 처리에서 빠져 있다. 서버가 채워야 한다.

- 조회 범위 밖의 과거. 프론트는 화면에 띄운 달만 조회한다.
- `계획상 비운동일`과 `운동 예정일에 쉼`의 구분. 날짜별 계획은 서버에만 있다(C-2).

임시로 구현한 것은 다음 세 가지다.

- **기록 없는 지난 날짜를 휴식으로 채운다.** `calendarReportModel.ts`가 `루틴 시작일 <= 날짜 < 오늘`이면서 세션 기록이 없는 날을 `rest`로 표시한다. 오늘과 미래는 채우지 않고, 왼쪽 경계인 `routineStartLocalDate`가 없으면 아무 날도 채우지 않는다.
  - 왼쪽 경계값은 프로필 생성일에서 파생했다. 개념은 `사용자가 서비스를 시작한 날`이며 백엔드가 같은 기준을 쓰기로 해도 된다. 다만 실제 서비스 기록 시작일은 서버가 확정한다.
- **안전 중단을 캘린더 전용 상태로 분리했다.** `STOPPED_FOR_SAFETY`를 `rest`로 접던 변환을 제거하고 `safety` 상태를 추가했으며, 색과 기호는 주간 리포트의 안전 중단 아이콘을 따른다. 주간 리포트가 이미 안전 중단을 별도 칸으로 세고 있어 두 화면이 같아졌다. 백엔드가 사용자 표시 기준을 `완료 / 부분 수행 / 휴식 / 안전 중단` 네 칸 배타로 맞춰도 된다.
  - **단, 표시 칸과 지표는 분리한다.** 캘린더는 하루에 아이콘을 하나만 그리므로 일부 블록을 완료한 안전 중단도 안전 중단 칸에만 들어간다. 이 날의 완료 블록이 지속률·보상·학습 입력에서 사라지면 안 된다(A-5). 조회 응답이 수행 결과와 안전 정보를 분리해 내려주면 프론트도 그 구조를 소비한다.
- **캘린더 집계 단위를 세션 수에서 일수로 바꿨다.** 화면의 아이콘 수와 통계 숫자가 어긋나지 않게 하기 위한 것이며, 서버가 일별 결과를 제공하면 자연히 같은 단위가 된다. 주간 리포트의 세션 수·안전 사건 수를 일수로 통일하라는 뜻은 아니다. 두 화면의 `휴식` 숫자는 단위가 달라 일치하지 않으므로 C-1·C-2의 단위 규정에서 확정한다.

## 4. 백엔드 정리 요청

### A. 공식 수행 결과와 안전 정보를 분리

1. 신규 결과의 표준 코드를 `COMPLETED` / `PARTIAL` / `REST`로 정리하고, 종료·상세·목록·홈 복원·주간 집계가 같은 서버 판정을 사용하게 한다.
2. `STOPPED_SAFETY`, `is_resumable=false`, Safety Event, 안내와 규칙 버전은 별도로 보존한다. `STOP_AND_SEEK_HELP`를 일반 휴식 안내로 낮추지 않는다.
3. 구형 `STOPPED_FOR_SAFETY`는 저장된 블록 증거로 결과를 복원한다. 일부 완료는 부분 수행, 0개는 휴식이다. 증거가 부족한 이력은 임의로 0개라고 간주하지 않고 별도 호환 처리·검증 대상으로 남긴다.
4. 신규 쓰기에서 `NOT_COMPLETED`와 `STOPPED_FOR_SAFETY`를 계속 병렬 생성하는 상태를 최종안으로 남기지 않는다. 필요한 구형 코드 지원에는 적용 범위와 제거 조건을 명시한다.
5. **안전 중단한 날의 완료 블록을 지표에서 버리지 않는다.** 지속률·조정 성공률·보상·다음 계획 학습 입력은 그날의 수행 결과(`PARTIAL` 또는 `REST`)를 기준으로 계산하고, 안전 중단 여부는 별도 축으로 유지한다. 통증을 참고 계속한 경우가 중단한 경우보다 지표상 유리해지면 안 된다. 현재 `persistence_rate`가 안전 중단을 제외하는 반면 보상은 부분 수행과 동일하게 지급하는 불일치(3.2)를 함께 해소한다.

### B. 중단 종료를 사유와 함께 확정

1. 0블록 일반 종료는 현재 `/not-completed`가 이미 사유를 받아 처리하므로 새 API가 필수는 아니다. 운동 후 **피드백**만 요구하지 않으면 된다. 경로를 정리한다면 종료 의도와 사유를 함께 받는 하나의 종료 API로 모으고, 정확한 형태는 계약 검토에서 확정한다.
2. 요청은 종료 의도를 전달하고 서버가 저장된 완료 블록을 읽어 결과를 판정한다. 클라이언트의 `REST` 요청만 믿고 완료 블록을 무시하면 안 된다.
3. 일반 종료와 안전 중단의 원인은 구별한다. 즉시 종료를 위해 `TIME_SHORTAGE`나 통증 사유를 임의로 자동 입력하지 않는다.
4. `/stop`의 기존 일반 중단은 `STOPPED_RESUMABLE`을 반환하므로 최종 종료와 혼용하지 않는다. 이번 흐름의 중단은 결과를 확정하고 홈/피드백으로 이동한다.
5. 중복 클릭·재시도에는 같은 종료 결과를 반환하고 세션·안전 사건·집계를 중복 생성하지 않는다. 블록 저장과 종료가 경합하면 서버가 원자적으로 처리한다.
6. 0블록 휴식에는 피드백 레코드가 없어도 종료·리포트·다음 계획 생성이 정상 동작해야 한다. 부분 수행 피드백 저장 실패 시에도 확정된 운동 기록은 유지한다.
7. **부분 수행으로 중단할 때도 사용자가 고른 중단 사유를 저장한다(3.1).** 종료 경로가 `/finish`든 통합 종료 API든 사유를 받을 자리를 두고, 사유 없는 종료도 계속 허용한다. 완료 블록 수가 사유 저장 여부를 좌우하지 않게 한다. 안전 중단은 Safety Event가 원인을 담으므로 사유를 중복 입력받지 않는다.

### C. 모든 휴식 경로를 동일한 조회·집계로 제공

1. 앱 미접속, 접속 후 루틴 미생성, 루틴 생성 후 운동 미시작, 0블록 종료, 기존 미수행·REST 선택 이력을 모두 같은 휴식 결과로 조회한다. 세션이 없다는 이유로 누락하거나 가짜 운동 세션·블록을 만들지 않는다.
2. 서버 권고 `action_code=REST`와 실제 휴식 기록의 확정 시점을 명시한다. 버튼이 사라진 이후에도 사용자 선택 API 호출을 전제로만 휴식을 저장하면 안 된다.
3. 캘린더·홈·주간 리포트가 공통 결과를 소비하도록 조회 계약을 제공한다. 권고 액션과 실제 결과를 혼동하지 않도록 필드 의미를 명시한다.
4. 완료·부분 수행·휴식은 같은 집계 단위에서 서로 배타적으로 센다. 안전 중단 수는 별도 지표이며 세 가지 수행 결과 합계에 다시 더하지 않는다.
5. 사용자 timezone, 일별 최종 결과, 동일 날짜의 여러 세션·REST 선택, 재체크인 시 중복 제거 기준을 명시한다. 현재 프론트는 날짜 아이콘과 세션 건수 집계를 혼용하므로 일수/세션 수를 계약에서 분명히 해야 한다.
6. 사유 없는 휴식을 정상 데이터로 처리한다. 새 흐름은 사유 입력 화면을 대부분 거치지 않으므로 미입력이 다수를 차지할 가능성과 선택 편향을 전제로 설계한다. 명시적 사유를 전체 휴식의 대표 원인으로 일반화하지 않는다. 상세 요청은 C-4를 따른다.
7. 일별 휴식 결과와 당일 압박 알림 차단을 분리한다. 알림 차단은 사용자의 명시적 당일 중단 의사 또는 기존 안전 조건이 발생한 시점부터 적용하며, 하루 마감의 휴식 판정을 기다리지 않는다. 상세 요청은 C-3을 따른다.

### C-1. 클라이언트 요청이 없는 날의 처리

- 일별 결과를 서버 책임으로 제공한다. 날짜 범위를 기준으로 읽을 때 결과를 산출하거나 일별 결과를 별도로 확정·저장할 수 있으며, 정확한 저장 방식은 백엔드가 결정한다. 필수 결과는 미접속 중에도 빠지지 않는 휴식 기록이다.
- 세션 테이블 조회나 REST 선택 API 호출만을 집계의 출발점으로 삼지 않는다. 루틴 생성 전 날짜도 포함할 수 있어야 하며, 예정 운동 행이 있다는 조건만으로 조회 범위를 제한하지 않는다.
- 접속 로그를 새로 수집해 미접속 여부를 추적할 필요는 없다. 위 네 사례를 서로 다른 사용자 상태나 필수 사유로 저장할 필요도 없다. 서버가 해당 날짜의 실제 완료 블록·결과를 기준으로 휴식을 판정한다.
- 오늘 휴식 상태에서 뒤늦게 운동해 블록을 완료하면 일별 결과를 갱신한다. 이전 휴식 분류를 한 건 더 남겨 같은 날짜를 휴식과 부분 수행·완료에 중복 집계하지 않는다. 개별 세션 이력과 안전 사건은 보존한다.
- 며칠간 미접속한 뒤 조회하거나 주간 리포트를 생성해도 그 날짜들이 빠짐없이 포함되어야 한다. 사용자가 다시 접속해야만 지난 휴식 날짜가 존재하는 구조를 피한다.
- 캘린더의 휴식 **일수**와 안전 중단 **세션 수** 등 집계 단위를 구분하고, 주간 완료율의 목표 운동 횟수 분모를 휴식 일수 증가만으로 임의 변경하지 않는다.

### C-2. 주간 목표와 계획상 휴식 구분 — PM·백엔드·프론트

문제는 휴식 4일이라는 숫자 자체보다 이를 미달 4회로 해석하는 것이다. 주 3회 목표를 모두 완료했다면 목표 달성률은 100%다. 나머지 4일의 휴식을 실패·벌점·조정 필요 근거로 사용하지 않는다.

- **권장 화면:** `목표 3회 중 3회 완료 · 목표 달성`, 보조 정보 `휴식 4일`. 휴식의 단위는 날짜 기반 `일`이며 운동 세션의 `회`와 구분한다. 완료율 분모에 7일 또는 휴식 일수를 넣지 않는다.
- 날짜별 계획이 명시적으로 저장되어 있을 때만 휴식의 보조 분류로 `계획상 비운동일`과 `운동 예정일에 쉼`을 제공한다. 둘 다 공식 수행 결과는 `REST`다. 상태 enum을 다시 미수행/휴식으로 갈라놓지 않는다.
- **주 N회 목표만으로 운동 요일을 추정하지 않는다.** 루틴 행·예정 운동 행이 없다는 이유만으로 그날이 계획상 비운동일이었다고 단정하지 않는다. 계획 정보가 없으면 세부 분류는 알 수 없음으로 두고 목표 대비 실제 수행만 평가한다.
- 백엔드는 당시 유효했던 날짜별 계획과 변경 이력을 기준으로 보조 분류를 산출한다. 나중에 바뀐 루틴으로 과거 휴식의 의미를 덮어쓰지 않는다. PM은 날짜 지정 없는 목표의 평가 기준을 확정한다.
- `weekly_reports/service.py`의 `weekday_failure_summary`, 개선 제안, 목표 달성률·지속률과 narration 입력을 함께 점검한다. 계획상 쉬는 요일을 `미완료가 많은 요일`로 지목하거나 모든 휴식을 실패 빈도로 계산하면 안 된다.
- 프론트 `WeeklyReportSummary.tsx`와 캘린더는 새 집계 단위·분류를 소비한다. 날짜별 계획 근거가 없는 동안에는 실패 요일·예정일 미실행 문구를 생성하지 않는다.

### C-3. 알림 차단의 기준 시점 — PM·백엔드 알림/운동·프론트

권장 규칙 문구: **“사용자가 오늘 운동을 그만두겠다고 명시한 시점부터 해당 사용자 로컬 날짜가 끝날 때까지 운동을 재촉하는 알림을 보내지 않는다. 안전 중단에 의한 차단도 유지한다.”** 공식 일별 휴식 여부는 이 규칙의 발동 조건이 아니다.

- 0블록 종료 명령이 성공하면 종료 기록과 당일 알림 차단 근거를 함께 저장한다. 피드백 저장이나 주간 집계가 완료될 때까지 기다리지 않는다.
- 부분 수행의 중단도 오늘 그만두겠다는 명시적 종료에 해당하면 같은 기준을 적용하는 것을 권장한다. 0블록만의 규칙으로 고정하지 않는다. 일시정지, 화면 이동, 단순 앱 종료를 당일 종료 의사로 추정하지 않는다.
- 미접속·루틴 미생성·운동 미시작으로 하루가 지난 뒤 정해진 휴식에는 과거 시점의 차단 의사를 만들어 넣지 않는다. 오늘의 기본 휴식 표시만으로 모든 사용자 알림을 아침부터 차단하는 처리도 하지 않는다.
- 현재 `workout_execution.py`의 `should_send_pressure_notification()`은 REST 선택 날짜를 보고, `db/repositories/workout.py`의 `is_pressure_notification_suppressed()`는 REST 선택과 안전 관련 근거를 조회한다. 일반 0블록 종료의 명시적 중단을 이 차단 경로에 연결해야 한다.
- `modules/notifications/service.py`의 주간 목표 재촉 알림 생성 시 같은 차단 근거를 조회한다. 예약 발송 경로가 있다면 실제 발송 직전에도 확인한다. 차단 전에 생성됐지만 아직 노출·발송되지 않은 재촉 알림의 취소/숨김 범위도 정한다.
- 차단 대상은 운동 재촉 알림이다. 안전 안내나 계정 관련 알림까지 일괄 차단하지 않는다. 새 기기와 재접속에서도 서버의 차단 근거를 적용한다.
- 로컬 날짜 경계와 같은 날 사용자가 자발적으로 다시 운동할 경우의 해제 정책은 PM·백엔드가 명시한다. 권장 기본값은 당일 재촉 차단 유지이며, 실제 운동 결과는 별도로 갱신한다. 안전 제한의 자동 해제 근거로 사용하지 않는다.
- 프론트는 중단 명령만 전달하고 사용자 부재를 의사 표현으로 만들어 전송하지 않는다. 재촉 차단을 위해 휴식 버튼·사유 질문을 되살리지 않는다.

### C-4. 휴식 사유의 결측과 선택 편향 — AI/데이터·백엔드·프론트

미접속·루틴 미생성·운동 미시작에는 사유를 묻는 화면이 없고, 최종 0블록 종료에서도 사유를 요구하지 않는다. 따라서 운동에 들어갔다 나온 사용자조차 항상 사유가 있는 것은 아니다. **사유 미입력이 다수일 것으로 예상되지만, 실제 비율은 운영 데이터로 확인할 값이다.** 입력된 소수의 사유도 자발적으로 입력했거나 구형 흐름을 이용한 사용자에 치우칠 수 있다.

- 백엔드는 사유 없는 휴식을 정상 집계하고, 사유가 없어서 리포트 생성·주간 마감을 실패시키는 검증을 제거한다. `UNKNOWN`을 피로·시간 부족·의욕 부족으로 대체하지 않는다.
- 집계 snapshot과 AI 입력에는 최소한 전체 휴식 일수, 명시적 사유가 있는 휴식 일수, 사유 미입력 일수, 사유가 수집된 경로·계약 버전을 구분할 정보를 제공한다. 휴식 일수와 사유 응답 건수를 섞어 비율을 계산하지 않는다. 새 민감정보 입력이나 접속 추적을 추가하지 않는다.
- 안전 사건과 부분 수행의 중단 사유는 전체 휴식 사유의 표본과 구별한다. 같은 날 여러 사유가 있는 경우 집계 단위를 정의하고 날짜를 중복 계산하지 않는다.
- `weekly_reports/service.py`의 `reason_counts`, `primary_miss_reason_code`, `blocker_reason_codes`, `weekday_failure_summary`와 `narration.py` 및 다음 계획의 입력을 함께 수정한다. `NOT_COMPLETED`를 `REST`로 이름만 치환해 기존 분석을 그대로 재사용하지 않는다.
- AI/데이터 담당자는 “응답자 내 가장 흔한 사유”를 “전체 휴식의 주된 원인”으로 해석하지 않도록 입력 계약·생성 검증·fallback을 변경한다. 최소 표본 조건을 충족해도 선택 편향이 사라지는 것은 아니다.
- 새 흐름의 기본값은 전체 휴식에 대한 대표 사유·인과 설명 생략이다. 충분한 명시적 응답이 있는 경우에도 `입력된 사유 N건 기준`의 제한된 요약만 허용하는 방향으로 검토한다. 노출 임계값은 AI/데이터·PM이 근거와 함께 확정한다.
- 다음 계획은 목표 대비 수행, 실제 완료 블록, 명시적인 운동 후 피드백 등 관찰 가능한 근거를 사용한다. 미입력 휴식 사유를 추정해 운동량을 자동 낮추거나 계획상 휴식을 실패 신호로 넣지 않는다.
- 프론트는 근거가 부족한 사유 분석을 숨기거나 `휴식 이유는 입력된 기록이 없어 분석하지 않았어요`처럼 한계를 표시한다. 이를 보완하려고 필수 사유 화면이나 추가 피드백을 도입하지 않는다.

### D. 호환 전환과 영향 범위

권장 순서는 계약 확정 → 백엔드 호환 읽기/새 쓰기와 migration → 프론트 전환 → 구형 클라이언트·데이터 확인 → 구형 코드 제거다. 응답 enum을 즉시 치환하면 기존 클라이언트가 깨질 수 있으므로 API 버전 또는 명시적인 호환 응답 전략이 필요하다.

| 영역 | 확인·정리할 경로 |
|---|---|
| 수행·안전 판정 | `backend/app/domain/rules/workout_execution.py` |
| 종료 및 선택 서비스·스키마·포트 | `backend/app/modules/workouts/{service,schemas,ports,codes}.py` |
| API 라우트 | `backend/app/api/v1/workouts.py` |
| 저장과 제약 | `backend/app/db/models/workout.py`, `backend/app/db/repositories/workout.py`, `backend/migrations/` |
| 주간 집계·학습 입력 | `backend/app/modules/weekly_reports/`, `backend/app/db/repositories/weekly_report.py`, `backend/app/domain/rules/weekly_report.py` |
| 명시적 중단에 따른 알림 차단 | `backend/app/modules/notifications/service.py`, `backend/app/db/repositories/workout.py`, `backend/app/domain/rules/workout_execution.py` |
| 후속 소비자 | `NOT_COMPLETED`/REST를 소비하는 복귀·피드백 조정·보상·알림·예정 운동 상태·종료 코드 목록·멱등 응답 |
| 동시 갱신 문서 | `SERVICE_POLICY_SAFETY_AND_ADAPTATION_V1.md`, `DOMAIN_RULES.md`, `API_CONTRACT.md`, `DATA_MODEL.md`, 관련 ADR·API 예시 |

DB 제약과 기존 데이터를 함께 검토하고 migration의 rollback 또는 forward-fix를 명시한다. 안전 사건·규칙 버전·실제 완료 블록을 삭제하지 않는다. 기존 리포트 snapshot의 유지/재생성/조회 변환 방식을 정해 과거 보고서가 새 집계와 불일치하는 문제도 처리한다.

현재 정책 문서에는 `NOT_COMPLETED`, 일반 중단 후 이어하기, 모든 중단 후 공통 피드백이라는 이전 흐름이 남아 있다. 최종 요청에 맞춰 이 부분을 함께 갱신해야 한다. 이 전달 문서 자체를 공개 계약 변경 완료나 새로운 안전 판단 규칙 승인으로 취급하지 않는다. 공동 검토 범위는 저장소 `docs/README.md`와 `docs/COLLABORATION_GUIDE.md`를 따른다.

## 5. 백엔드 반영 후 프론트 후속 정리

- typed API와 mock을 확정된 새 계약으로 변경한다.
- `WorkoutScreen.tsx`의 중단 흐름을 확정된 종료 API에 맞춘다. 완료 블록 수와 무관하게 중단 사유를 함께 보내고, 0블록 종료에서 운동 후 피드백 화면을 거치지 않는다.
- `SessionResultScreen.tsx`, `MainFlow.tsx`의 휴식 분기를 새 공식 결과로 전환한다.
- 3.4의 임시 처리를 모두 제거한다. 클라이언트의 지난 날짜 휴식 채우기, 캘린더 전용 `safety` 상태, 캘린더 자체 일수 집계를 서버 일별 결과로 교체한다.
- 세션 목록만으로 날짜 결과를 만드는 경로를 서버 일별 결과 조회로 교체해, 미접속·루틴 미생성·운동 미시작 날짜도 휴식으로 표시한다.
- 캘린더가 수행 결과와 안전 정보를 각각 표시하도록 바꾼다. 일부 블록을 완료한 안전 중단은 부분 수행으로 세고 안전 중단은 보조 표식으로 함께 보여준다.
- 캘린더와 주간 리포트의 집계 단위를 계약에 맞춰 통일하고, 화면 문구에 `일`과 `회`를 구분해 표기한다.
- `WeeklyReportSummary.tsx`의 `counts.not_completed → 휴식` 호환 매핑을 새 휴식 집계로 교체하고, 안전 중단은 별도 보조 지표로 유지한다.
- 앱 재실행 후 홈·캘린더·리포트가 같은 결과와 안전 안내를 복원하는지 검증한다.
- 제거한 휴식 진입점을 되살리지 않는다. 보존한 디자인은 계속 미렌더링 상태로 둔다.

## 6. 공동 검증 인수 조건

| 검증 | 기대 결과 |
|---|---|
| 여러 날 앱 미접속, REST 선택·종료 요청 없음 | 해당 날짜 모두 휴식으로 조회·집계, 주간 리포트에서 누락 없음 |
| 접속했지만 루틴을 생성하지 않음 | 결정·루틴·세션 행 없이도 해당 날짜 휴식 |
| 루틴 생성 후 운동을 시작하지 않음 | 운동 세션 생성 여부와 무관하게 휴식 |
| 오래 운동했지만 0블록 완료 후 중단 | 중단 사유와 함께 휴식 저장, 운동 후 피드백 없이 홈 복귀 |
| 일부 블록 완료 후 사유를 골라 중단 | 부분 수행 저장과 함께 중단 사유 보존, 완료 블록 수 때문에 사유가 유실되지 않음 |
| 일부 블록 완료 후 중단 | 부분 수행 저장, 피드백 선택 전 버튼 비활성화, 저장 성공 후 홈 |
| 전체 블록 완료 | 완료 저장, 동일한 피드백 저장 흐름 |
| 0블록 안전 중단 | 휴식 + 안전 사건 보존, 피드백 생략, 안내와 재개 금지 유지 |
| 일부 블록 완료 후 안전 중단 | 부분 수행 + 안전 사건, 캘린더에서 휴식으로 덮어쓰지 않음 |
| 구형 안전 중단 이력 | 블록 증거 기반 결과 복원, 안전 정보 보존 |
| 과거 REST 선택과 0블록 종료 | 같은 휴식 분류로 조회, 합의된 날짜/세션 기준으로 중복 방지 |
| 사유·피드백 없는 휴식의 주간 리포트 | 생성·확인·다음 계획 연계 성공, 가짜 사유 없음 |
| 앱 재실행·다른 기기 조회 | 홈·캘린더·리포트 결과 및 안전 정보 일치 |
| 종료 재시도·블록 저장 경합 | 결과 일관성, 중복 기록 없음, 실패 시 재시도 가능 |
| 호환 클라이언트와 기존 리포트 | 합의한 전환 기간의 읽기·응답 호환 유지 |
| 오늘 휴식 상태에서 운동을 시작해 일부/전체 블록 완료 | 부분 수행/완료로 갱신, 같은 날 휴식 중복 집계 없음 |
| 미래 날짜·진행 중 세션 | 미래 휴식 실적 없음, 휴식 표시로 진행 세션 강제 종료 없음 |
| 주 3회 목표, 완료 3회, 휴식 4일 | 목표 달성률 100%, 휴식을 미달 4회로 설명하지 않음 |
| 날짜별 계획이 없고 주간 목표만 존재 | 특정 요일을 예정 운동일/계획상 휴식일로 추정하지 않음 |
| 계획상 비운동일에 휴식 | 실패 요일·대표 장애 요인·자동 하향 조정 근거에서 제외 |
| 낮에 0블록 종료, 피드백 없음 | 명시적 중단 시점부터 당일 재촉 알림 차단, 다음 로컬 날짜 경계 처리 |
| 미접속으로 일 마감 때 휴식 확정 | 과거 시점의 중단 의사를 생성하지 않음, 오늘 기본 휴식 표시로 무조건 차단하지 않음 |
| 휴식 사유 0건 또는 소수만 입력 | 리포트 정상 생성, 전체 휴식 원인 추정 생략, 응답 범위·결측 보존 |
| 5블록 중 3블록 완료 후 안전 중단 | 완료 3블록이 지속률·조정 성공률·보상·학습 입력에 반영, 참고 계속한 경우보다 불리해지지 않음 |
| 캘린더 휴식 일수와 리포트 휴식 수 | 집계 단위가 계약에 명시되고 화면 문구가 `일`/`회`를 구분, 같은 단어의 숫자 차이가 설명 가능 |
| 프론트 임시 처리 제거 후 재검증 | 3.4의 세 항목을 제거해도 캘린더가 서버 일별 결과만으로 동일하게 표시 |

백엔드 formatter/linter/type checker, 도메인 단위 테스트, 종료·안전·목록·주간 API 통합 테스트, migration 검증, 관련 안전 불변식 테스트를 실행한다. 프론트는 새 계약에 맞춘 컴포넌트·흐름 테스트와 모바일 build를 다시 실행한다.

## 7. 이번 전달 문서의 검증 범위

현행 도메인 규칙, 서비스, 스키마, 저장 모델, 프론트 분기와 계약 문서를 읽어 위 차이를 확인했다.

2026-09-08 기준 이번 회차에서 실제로 변경한 것은 문서와 **프론트 캘린더 표시뿐이다**(3.4). 백엔드 동작, API, DB, 공개 계약, 개인정보 수집·로깅은 변경하지 않았다. 프론트 변경은 `frontend` 기준 type checker, linter, 전체 컴포넌트·모델 테스트, formatter로 검증했다. 후속 백엔드 구현과 실서버 통합 검증은 아직 수행하지 않았다.
