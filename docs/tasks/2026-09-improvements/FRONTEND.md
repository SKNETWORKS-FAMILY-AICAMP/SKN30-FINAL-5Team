## FE-1. 운동 상세 화면 구성 순서와 가독성

- 선행: **BM-2**
- 파일: `frontend/src/features/workout/ExerciseDetailSheet.tsx` (208줄, 충돌 없음)

### 개선 항목

> 운동 자세 설명: 주요부위 / 자세 설명(번호별 줄바꿈 가독성 개선) / 주의사항 순서로 나타내도록

### 현재 상태

`ExerciseDetailSheet.tsx`의 렌더 순서가 요청과 다르다.

| 현재 | 줄 | 요청 |
|---|---|---|
| 자세 설명 (`instruction_summary`, 한 덩어리 문자열) | 48 | 1. 주요 부위 |
| 주요 부위 | 50 | 2. 자세 설명 (단계별 줄바꿈) |
| `form_cues` (라벨 없는 목록) | 57 | 3. 주의사항 |

그리고 API가 이미 내려주는 `household_equipment_guides`를 **전혀 렌더링하지 않는다.**
생활도구 안내가 붙는 34개 운동에서 승인된 제안·예시·주의사항이 화면에 나오지 않고 있다.

### 목표

BM-2가 추가하는 `instruction_steps`와 `cautions`를 써서 요청된 순서로 표시한다.

### 요구

- **문자열을 프론트에서 파싱하지 않는다.** 단계 분리는 BM-2가 백엔드에서 한다.
  `instruction_steps`가 없는 구버전 응답을 만나면 `instruction_summary`를 그대로 한 덩어리로
  표시하는 폴백을 둔다.
- 단계는 번호와 함께 줄을 나눠 표시한다.
- `form_cues`를 라벨 없는 목록이 아니라 "주의사항"으로 명시한다.
- 생활도구 가이드가 있으면 제안·예시·주의사항을 표시한다.
- GIF 이미지 영역은 현재 동작을 유지한다.

### 인수 조건

1. 표시 순서가 주요 부위 → 자세 설명 → 주의사항이다.
2. 각 단계가 별도 줄로 보이고 번호가 붙는다.
3. 주의사항에 라벨이 있다.
4. 생활도구 가이드가 있는 운동에서 가이드 내용이 보인다.
5. `instruction_steps`가 없는 응답에서도 화면이 깨지지 않는다.
6. 로딩·에러·권한 없음 상태가 유지된다 (AGENTS.md 6절).

### 제외 범위

콘텐츠 문구 수정. 이미지 처리 변경. 백엔드 계약(BM-2).

## FE-2. 변형 운동 노출을 집 운동으로 한정

- 선행: **BM-3**
- 파일: `frontend/src/features/workout/ExerciseVariants.tsx` (315줄)

### 목표

BM-3이 빈 목록을 반환하는 맥락에서, 변형 운동 진입점 자체를 노출하지 않는다.

### 요구

빈 목록을 "결과 없음" 문구로 보여주는 것과, 진입점을 숨기는 것은 다르다. 헬스장 세션에서는
**진입점을 숨긴다.** 사용자가 눌렀는데 빈 화면이 나오는 경험을 만들지 않는다.

### 인수 조건

1. 집 운동 맥락에서 기존과 동일하게 변형 운동을 볼 수 있다.
2. 헬스장·야외 맥락에서 변형 운동 진입점이 보이지 않는다.
3. 목록이 실제로 비어 있는 경우(집 운동인데 대체가 없음)와 맥락상 숨기는 경우가 구분된다.
4. 조회 실패 시 에러 상태가 표시된다.

## FE-3. 체크인 위험 신호 질문 중복 제거

- 선행: 없음 (FE-14 이후 권장)
- 파일: `frontend/src/features/home/HomeScreen.tsx:2961-2986`

### 개선 항목

> 동일한 질문이 반복돼서 "위 증상이 있나요?"를 빼고 그냥 위 위험 박스에 예/아니오 버튼 같이
> 넣어도 될 듯합니다.

### 현재 상태

같은 질문이 세 번 나온다.

```
2962  제목:   "오늘 위험 신호가 있나요?"
2964  본문:   "오늘 가슴 통증이나 ... 심장이 매우 빠르거나 불규칙하게 뛰는 느낌 같은 증상이 있나요?"
2969  라벨:   "위 증상이 있나요?"        <- ChoiceBlock label
2971  버튼:   "없어요" / "있어요"
```

### 목표

`ChoiceBlock`의 `"위 증상이 있나요?"` 라벨을 없애고, 없어요/있어요 버튼을 `redFlagSection` 박스
안으로 옮긴다.

### 반드시 지킬 것 (AGENTS.md 7절)

- 통증·이상반응 화면은 **진지한 톤**을 유지한다. 이 섹션에 장난스러운 요소를 넣지 않는다.
- 미선택 경고("위험 신호 여부를 선택해주세요.")는 그대로 유지한다. 이 질문은 건너뛸 수 없다.
- 접근성 라벨("위험 신호 없어요" / "위험 신호 있어요")을 유지한다. `ChoiceBlock` 라벨을 지우면
  스크린 리더가 맥락을 잃을 수 있으므로, 박스 자체가 접근성 그룹으로 묶이는지 확인한다.

### 인수 조건

1. 질문 문구가 두 번(제목 + 본문)만 나온다.
2. 없어요/있어요 버튼이 위험 신호 박스 안에 있다.
3. 선택하지 않으면 저장이 막히고 경고가 뜬다.
4. 스크린 리더로 두 버튼의 의미를 구분할 수 있다.
5. 위험 신호 "있어요" 선택 시의 기존 안전 플로우가 변하지 않는다.

### 제외 범위

위험 신호 문구 자체의 의학적 표현 수정 (PM·도메인 검토 필요). 안전 판정 로직.

## FE-4. 체크인 장소 선택 UI

- 선행: **BM-4** / 게이트: **G7 확정**
- 파일: `frontend/src/features/home/HomeContainer.tsx:388-395`, `HomeScreen.tsx:2827-2830`

### 확정된 결정 (G7)

> 온보딩에서 집·헬스장 선택 자체를 제거, 운동 장소는 **체크인 화면에서 헬스장/집을 선택할 수 있게
> 표시돼야 함.**

### 원인은 여기다

체크인 장소 선택지가 프로필에 묶여 있다. 프로필은 ADR-0017 이후 더 이상 장소의 권위가 아니다.

```ts
// HomeContainer.tsx:388  — 제거 대상
const locationCodes = useMemo(() => (
  profile == null ? []
    : profile.available_location_codes.length > 0
      ? profile.available_location_codes
      : [profile.preferred_location_code]
), [profile]);
```

온보딩 화면에는 이미 장소 입력이 없으므로 온보딩 쪽은 손댈 것이 없다.

### 목표

체크인에서 헬스장·집을 항상 고를 수 있게 한다. 프로필 값을 참조하지 않는다.

### 요구

- 선택지 목록을 **하드코딩하지 않는다.** BM-4가 서버 응답으로 준다.
- 노출 대상은 **집과 헬스장 둘뿐이다.** `OUTDOOR`는 표시하지 않는다 (2026-09-07 확정).
  값 자체는 백엔드에 남으므로 프론트 타입에서도 지우지 않는다.
- 프로필에서 가져오던 경로(`HomeContainer.tsx:388`)를 걷어낸다.
- 기본 선택값을 정한다. 전날 체크인의 장소를 기본값으로 쓰는 것을 권장한다
  (`latestContext?.location_code`가 이미 폴백 체인에 있다, `HomeContainer.tsx:530`).
- 장소를 고르지 않고 저장할 수 없게 할지 결정한다. 지금은 폴백 체인이 값을 채워 넣는다.

### 인수 조건

1. 프로필에 장소가 없어도 체크인에서 헬스장·집을 고를 수 있다.
2. 선택지에 야외가 나타나지 않는다.
3. 선택지가 서버 응답에서 온다.
4. 선택한 장소가 저장되고 다음 날 기본값으로 반영된다.
5. `profile.available_location_codes`를 읽는 코드가 체크인 경로에 남아 있지 않다.
6. 온보딩이 그대로 완료된다 (장소 입력이 원래 없으므로 영향 없음).

## FE-5. 마이페이지 ADR-0017 정리 (성별 · 키 · 운동 장소)

- 선행: **BL-7** / 게이트: **G7 확정**
- 파일: `frontend/src/features/home/MyPageProfileEditor.tsx`,
  `frontend/src/features/home/myPageModel.ts`, `MyPageContainer.tsx`

### 보고된 문제

> 마이페이지에서 프로필 수정할때 아직 키, 성별 남아있음

프로필 사진 문제는 원인이 전혀 다르므로 **FE-15로 분리했다.**

### 취향 문제가 아니라 미완 실행이다

`docs/adr/0017-onboarding-input-reduction-and-ungated-base-routine.md`(**ACCEPTED**, 2026-09-02)가
성별·키·장소를 수집 대상에서 제외하기로 이미 결정했다. 온보딩 화면에서는 제거됐지만
**마이페이지에는 남아 있다.** 사용자가 본 것이 그 잔여다.

### 제거 대상

| 항목 | 위치 |
|---|---|
| 성별 | `MyPageProfileEditor.tsx:536` (`BASIC_SEX_OPTIONS`) |
| 키(cm) | `MyPageProfileEditor.tsx:552` |
| 운동 장소 수정 | `MyPageProfileEditor.tsx:76, 241-255` |
| 운동 장소 요약 행 | `myPageModel.ts:44-47` |

### 반드시 남길 것

**체중(kg)은 남긴다.** BM-6의 칼로리 계산이 체중을 쓴다 — G3이 "체중과 수행한 운동 기준"으로
승인했다. ADR-0017의 제거 목록에도 체중은 없다. `MyPageProfileEditor.tsx:562`의 체중 입력을
실수로 함께 지우지 않도록 주의한다.

생년월일도 남긴다. 연령 적격성 판정에 쓰인다.

### 요구

- 백엔드 응답 필드는 그대로 둔다. **입력 UI만 제거**한다. 응답 필드 제거는 BL-7 2단계다.
- 개인정보 안내 문구를 남은 항목과 맞춘다. 현재 문구는
  `"생년월일·성별·키·체중은 개인정보 보호를 위해 기존 값을 다시 보여주지 않아요"`인데,
  성별·키가 사라지면 사실과 어긋난다.
- 마이페이지 요약 행에서도 운동 장소를 뺀다. 요약에만 남으면 사용자가 바꿀 수 없는 값을 계속
  보게 된다.

### 인수 조건

1. 프로필 수정에 성별·키 입력이 없다.
2. 체중과 생년월일 입력은 그대로 있다.
3. 마이페이지에 운동 장소 항목이 요약·수정 어디에도 없다.
4. 개인정보 안내 문구가 남은 항목과 일치한다.
5. 프로필 저장이 정상 동작하고, 제거된 필드를 요청에 넣지 않는다.
6. 타입 체크와 프로덕션 빌드가 통과한다.

### 제외 범위

프로필 응답 필드·컬럼 제거(BL-7 2단계). 체중 제거. 프로필 사진(FE-15).

## FE-6. 운동 시간 90분 UI와 권장 안내

- 선행: **BM-1** (G4 이후)
- 파일: `HomeScreen.tsx` 체크인 시트 (FE-14 분할 후엔 해당 파일)

### 목표

체크인의 운동 시간 선택 범위를 90분까지 넓히고, 권장 시간을 안내한다.

### 요구

- 권장 시간 값을 **프론트에서 하드코딩하지 않는다.** BM-1이 응답으로 준다.
- 권장을 넘는 시간을 고를 수 있어야 한다. 권고이지 제한이 아니다.
- 권장을 넘겼을 때의 안내 문구는 사용자를 탓하지 않는다 (AGENTS.md 7절).
- 마이페이지의 기본 운동 시간 설정과 값 범위가 어긋나지 않게 한다.

### 인수 조건

1. 체크인에서 90분까지 선택할 수 있다.
2. 권장 시간이 표시되고, 그 값이 서버 응답에서 온다.
3. 권장을 넘는 선택이 차단되지 않는다.
4. 서버가 90분 계획 생성에 실패하면 에러 상태가 표시되고, 조용히 짧은 루틴이 나오지 않는다.
5. 권장 시간 정보가 없는 응답에서도 화면이 동작한다.

3. 로그인 실패·취소·네트워크 오류 각각의 상태가 표시된다.

### 인수 조건

1. 사진을 바꾸면 마이페이지와 홈 헤더에 즉시 반영된다.
2. 저장에 실패하면 실패가 표시되고, 성공으로 보이지 않는다.
3. 이미지 저장만 실패한 경우와 프로필 전체가 실패한 경우가 구분된다.
4. 실패 후 다시 시도할 수 있다.
5. 이미지 URL이나 사용자 식별자가 로그에 남지 않는다.

### 제외 범위

이미지 리사이즈·크롭. CDN 도입. 백엔드 수정과 IAM(BL-5).
