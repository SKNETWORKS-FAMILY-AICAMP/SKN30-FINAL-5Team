# MVP_SCOPE.md

## 1. 문서 목적

이 문서는 초기 MVP에서 반드시 구현할 기능, 선택 기능, 제외 기능, 완료 조건과 일정 지연 시 삭제 순서를 정의한다.

제품 요구는 PROJECT_BRIEF.md, 도메인 정책은 DOMAIN_RULES.md, API는 API_CONTRACT.md, 데이터 구조는 DATA_MODEL.md를 따른다.

본 문서와 다른 참고 기획서의 범위가 충돌하면 이 문서의 MVP 분류를 적용하고 팀 합의 없이 범위를 확대하지 않는다.

---

## 2. MVP 검증 가설

> 사용자의 운동 계획이 당일 현실 조건과 충돌할 때, 여러 전문 에이전트가 안전을 우선하면서 목표를 보존하는 축소·변경안을 제공하면 완전 포기를 줄이고 운동 복귀를 도울 수 있는가?

---

## 3. 고정 제품·기술 조건

- 만 14세 이상 운동 입문자와 복귀자를 대상으로 한다.
- 백엔드는 Python, FastAPI, Pydantic, SQLAlchemy, Alembic을 사용한다.
- PostgreSQL을 주 데이터베이스로 사용한다.
- 백엔드는 모듈형 모놀리스로 구성한다.
- 전문 proposal 에이전트는 Training, Recovery, Safety로 구성한다.
- Coordinator(의장 에이전트)는 세 proposal을 취합해 검증된 후보 중 최종 추천안 한 개를 선택한다.
- 안전, 통증 제외, 시간 계산, 복귀 모드는 결정적 Python 규칙이다.
- 사용자가 요청한 운동 시간은 계획 목표로 유지하며 시스템이 임의로 더 짧은 시간으로 변경하지 않는다.
- 예상 시간과 실제 경과 시간은 정보값이며 운동 완료 판정에 사용하지 않는다.
- LLM은 안전 판단을 내리거나 안전 veto를 무시할 수 없다.
- MVP 계획 선택은 LLM 없이 동작해야 한다.
- 웨어러블 연동 요약 경로를 MVP에 포함하되, 웨어러블 없이도 전체 핵심 흐름이 동작해야 한다.
- 연동 기기·API·출처·품질·라이선스는 후보 탐색 후 개발 전에 확정하며, 권한 거부·미연동 사용자는 수동 입력 경로를 사용한다.
- 프론트엔드는 React Native, TypeScript, Expo Development Build를 기본으로 한다.
- 프론트 담당자가 React Native 경험이 전혀 없어 Flutter로 바꿔야 한다면 본격 구현 전에 한 번만 결정하며 프로젝트 중간에는 프레임워크를 변경하지 않는다.
- 인증은 Firebase Authentication을 사용하고 백엔드가 Firebase ID Token을 검증한다.
- Google은 Firebase 기본 provider를 사용하고 Kakao/Naver는 백엔드 provider adapter를 통해 Firebase custom token으로 연결한다.
- Redis, Celery, 별도 에이전트 서비스는 핵심 MVP 기본 구성에 포함하지 않는다.

## 4. 핵심 사용자 흐름

~~~text
Firebase 로그인
-> 연령 적격성 확인과 온보딩
-> 검수된 운동 데이터 기반 기본 루틴
-> 오늘의 체크인
-> 전문 에이전트 제안
-> 결정적 조정과 최종 안전 검증
-> 최종 추천안 확인 또는 휴식 선택
-> 운동 실행 또는 휴식
-> 완료, 중단 또는 미수행
-> 피드백 저장
-> 다음 결정과 복귀 정책에 반영
~~~

이 흐름은 실제 React Native 프론트엔드, FastAPI, PostgreSQL, 에이전트 모듈로 끝까지 연결되어야 한다.

## 5. 반드시 구현할 기능

### 5.1 인증과 계정

- Firebase Authentication 로그인
- Firebase ID Token 백엔드 검증
- 내부 UUID 사용자와 Firebase subject 연결
- Google 로그인
- Kakao 로그인
- Naver 로그인
- provider-neutral 사용자 identity 연결
- 가입 후 14일 AI 코치 무료 체험(POL-013 승인 범위)
- Premium 결제·구독은 MVP 이후 확장으로 분리
- 계정 삭제 요청
- 삭제 요청 즉시 접근 차단
- 사용자 연결 운영 데이터 7일 이내 삭제
- 백업 최대 30일 순환 소멸 정책

인증 토큰, 이메일, 전체 이름을 로그에 기록하지 않는다.

### 5.2 온보딩

필수:

- 닉네임
- 만 14세 이상 이용 자격 확인
- 운동 목표
- 운동 경험
- 연령대(만 14세 이상 허용 코드)
- 선호 장소
- 보유 장비
- 기본 희망 운동 시간
- 주간 희망 운동 횟수
- 주의 또는 불편 부위

선택:

- 선호 운동 유형
- 코치 문구 성향
- 키
- 체중
- 성별

코치 문구 성향 기본값은 SUPPORTIVE이며 SUPPORTIVE, CONCISE, ENERGETIC 중 선택한다. 문구 성향은 안전 판단과 운동 강도에 영향을 주지 않는다.

정확한 생년월일은 수집하지 않는다. 체중이 입력된 경우에만 예상 소모 칼로리 추정에 사용할 수 있으며, 체중이 없으면 API·저장 값은 `null`로 두고 수기활동 상태는 `UNKNOWN`으로 기록한다. 체중·성별은 안전 판정이나 의료적 결론에 사용하지 않는다.

일반 개인정보, 민감정보, 웨어러블 연동, 캘린더 연동, 마케팅 동의는 서로 분리해 기록한다. 민감정보·웨어러블·캘린더 동의 철회 시 해당 수집·동기화를 즉시 중단하고 비연동 경로를 제공한다.

### 5.3 운동 데이터

초기 통합용 데이터:

- 30~50개

MVP 통합 목표:

- 50~80개

필수 정보:

- 운동 코드와 표시명
- 운동 유형: 근력, 유산소, 가동성 등
- 운동 초점: 상체, 하체 등 루틴 화면 분류
- 주·보조 운동 부위
- 운동 패턴
- 난이도
- 초보자 적합 여부
- 장비
- 장소
- 반복 또는 시간 기반 수행 방식
- 동작 시간 추정 메타데이터
- 세트 간 휴식
- 동작 전환 시간
- 목표 태그
- 대체 운동
- 통증 부위별 제외·주의 규칙
- 회복안 사용 가능 여부
- 출처와 라이선스
- 검수 상태와 버전
- 펼침용 자세·수행 설명, 핵심 자세 포인트와 콘텐츠 버전
- 선택적 검수 이미지·애니메이션 참조
- 운동 실행 중앙에 표시할 마스코트 애니메이션 참조

CORE, SUPPORT, OPTIONAL은 운동 자체의 고정 속성이 아니라 루틴 항목의 목표상 역할로 저장한다.

검수 상태:

~~~text
DRAFT
TECH_REVIEWED
DOMAIN_APPROVED
REJECTED
DEPRECATED
~~~

프로덕션 추천에는 DOMAIN_APPROVED 운동, 대체 관계, 안전 규칙, 회복 콘텐츠만 사용한다.

예상 소모 칼로리는 운동 종류·운동 시간·강도와 사용자가 제공한 체중을 이용한 추정치로 제공한다. 정밀 칼로리 계산이 아니며 진단 또는 안전 판정의 단독 근거로 사용하지 않는다. 산식과 계수는 버전 관리하고 개발 전 확정한다.

승인 흐름:

~~~text
개발팀장·백엔드+데이터 초안
-> 백엔드 기술 검토
-> PM 출처·라이선스·문구 검토
-> 외부 운동·보건 전문가 안전 승인
~~~

### 5.4 기본 루틴

지원 범위:

- 홈트
- 헬스장
- 걷기와 가벼운 러닝
- 스트레칭과 코어

기본 루틴은 사용자 목표, 경험, 장소, 장비와 검수된 운동 데이터만 사용해 보수적으로 생성한다.

캘린더 연동은 빈 시간 후보를 제안하고 운동 계획을 등록하는 MVP 기능이다. 주간 목표의 특정 요일을 강제하지 않으며, 캘린더 기록은 공식 수행 상태를 변경하지 않는다.

루틴 화면은 먼저 근력·유산소 등 큰 운동 유형과 상체·하체 등 초점을 보여주고, 그 아래에 랫 풀 다운·레그 프레스 같은 세부 운동을 순서대로 배치한다. 각 운동은 세트·반복 또는 유산소 권장 목표를 가진다.

### 5.5 오늘의 체크인

필수:

- 주관적 피로: LOW, MODERATE, HIGH
- 희망 운동 시간 확인 또는 사용자의 명시적 당일 변경
- 불편 부위와 심각도
- 중대한 이상 반응 여부

선택:

- 당일 장소 변경
- 수면 시간
- 공복
- 수분

불편 부위는 여러 개를 선택할 수 있다. 심각도는 NONE, MILD, MODERATE, SEVERE 제품 척도를 사용하며 의료적 통증 척도로 해석하지 않는다.

상세 신체 부위와 이상 반응 코드는 DOMAIN_RULES.md를 따른다.

### 5.6 전문 에이전트

- TrainingAgent
- RecoveryAgent
- SafetyAgent
- Coordinator(의장 에이전트)

각 에이전트는 구조화된 proposal을 반환한다. 자유 형식 운동 계획을 반환하지 않는다.

현재 멀티 에이전트 로직은 설계 전 단계다. 에이전트별 입력·출력, 조정 순서, 버전 필드, 공개 요약의 상세 계약은 멀티 에이전트 로직 설계 후 확정하며, 그 전까지 관련 문서와 테스트는 잠정 상태로 관리한다.

### 5.7 조정과 최종 안전 검증

최종 액션:

~~~text
KEEP
DOWNSHIFT
CHANGE
RECOVERY
REST
STOP_AND_SEEK_HELP
~~~

조정 결과:

- 최종 추천 루틴 1개
- 변경 이유 최대 2개
- 내부 후보의 안전 검증 결과

예외:

- REST에는 운동 계획을 제공하지 않는다.
- STOP_AND_SEEK_HELP에는 운동 계획과 선택 가능한 운동 옵션을 제공하지 않는다.
- RECOVERY의 최종 추천안은 검수된 저강도 회복 계획이다.

회복·안전 에이전트의 판단 후 독립된 최종 안전 게이트를 다시 실행한다.

초기 루틴 생성과 조정 과정에는 에이전트별 요약 의견과 최종 조정 이유를 보여주는 회의 UI를 MVP에 포함한다. 내부 프롬프트와 숨은 추론은 노출하지 않으며 구체 UI 표현은 멀티 에이전트 로직 설계 후 확정한다.

### 5.8 목표 보존형 다운시프트

다운시프트는 운동 시간을 자동으로 줄이는 기능이 아니라, 사용자가 요청한 시간을 유지하면서 당일 상태에 맞게 수행 부담을 낮추는 기능이다.

조정 순서:

~~~text
안전·장비·장소 충돌 제거
-> 사용자 requested_duration_minutes 유지
-> 외부 부하·강도 하향
-> 세트·반복 또는 운동 난이도 조정
-> 검수된 대체 운동·운동 유형 조정
-> 휴식 구성 조정
-> CORE 목표와 운동 순서 보존
~~~

- 프로필의 기본 희망 시간은 당일 계획의 기본 `requested_duration_minutes`다.
- 사용자가 당일 시간을 직접 변경한 경우에만 그 값을 당일 목표로 사용한다.
- 최종 추천 루틴은 사용자가 요청한 requested duration을 유지한다.
- lighter 옵션을 별도 공개하지 않고, 다운시프트가 필요한 경우 최종 추천 루틴 자체의 부하·강도·세트·반복·운동 유형·휴식 구성을 조정한다.
- 시스템은 40분을 임의로 15분이나 5분으로 바꾸지 않는다.
- 시간 부족 미수행이 반복돼도 사용자 확인 없이 희망 시간을 자동 변경하지 않는다.
- 정확한 예상 시간은 운동 종류와 사용자 속도에 따라 달라질 수 있으므로 권장값으로 표시한다.
- 안전하게 시간을 채울 수 없다는 이유로 불필요한 운동을 추가하지 않는다.

SEVERE 불편이나 중대한 이상 반응처럼 운동 제공 자체가 안전하지 않으면 시간 선호보다 REST 또는 STOP_AND_SEEK_HELP가 우선한다.

### 5.9 권장 시간과 실제 경과 시간

사용자가 입력한 시간은 원하는 운동 길이인 `requested_duration_minutes`다. 서버는 계획 구성을 위한 `estimated_duration_seconds`를 계산하지만 이는 권장값이다.

~~~text
estimated_duration_seconds
= 장비 준비
+ 준비 운동
+ 실제 동작
+ 세트 간 휴식
+ 동작 간 전환
+ 마무리 운동
~~~

MVP 기본 범위:

- 장비 준비: 0~60초
- 준비 운동: 60~180초
- 동작 전환: 동작당 10~20초
- 세트 간 휴식: 검수된 운동 데이터에 정의
- 마무리: 45~120초

계획기는 estimated duration이 requested duration에 가깝도록 구성하되 이를 절대 상한이나 완료 조건으로 사용하지 않는다. 허용 가능한 예상 시간 편차는 실제 운동 데이터 검증 후 정책값으로 확정한다.

운동 시작 시 클라이언트는 0초부터 증가하는 경과 타이머를 표시한다. 실제 경과 시간은 사용자가 운동량을 확인하고 세션 기록을 남기기 위한 값이며 다음을 결정하지 않는다.

- 운동 블록 완료 여부
- 세션 COMPLETED/PARTIAL/NOT_COMPLETED
- 안전 판단
- 사용자의 운동 중단 가능 여부

### 5.10 안전 처리

필수 규칙:

- 불편 부위와 충돌하는 운동 제외
- MILD 또는 MODERATE에서 검수된 대체 운동 사용
- SEVERE 또는 급성 근골격 신호에서 REST
- 중대한 이상 반응에서 STOP_AND_SEEK_HELP
- 사용할 수 없는 장비와 장소의 운동 제외
- 복귀 모드 상한 초과 금지
- 검수되지 않은 운동과 안전 규칙 제외
- 안전한 후보가 없으면 REST
- 안전 veto된 원래 계획 선택 차단

안전 화면은 검수된 serious tone 문구를 사용하고 마스코트의 장난스러운 애니메이션을 중단한다.

### 5.11 운동 실행

- 루틴의 큰 분류: 근력·유산소·가동성 등 운동 유형과 상체·하체 등 초점
- 순서가 있는 운동 블록 목록
- 각 블록의 운동명, 세트, 반복 또는 유산소 권장 목표
- 각 블록 상단의 자세·설명 펼침 버튼
- 화면 최상단의 0초부터 증가하는 전체 경과 타이머
- 경과 타이머 일시정지·재개
- 화면 중앙의 현재 운동 마스코트 애니메이션
- 화면 하단의 추천 운동 블록과 다음 운동
- 체크 버튼, 블록 격파 또는 좌측 밀기 제스처를 통한 블록 완료
- 완료 후 다음 PENDING 블록으로 이동
- 선택적 휴식 타이머는 보조 정보로만 제공
- 운동 중 불편·이상 반응 보고
- 안전 중단
- 네트워크 오류 시 진행 상태 임시 보존

전체 경과 타이머의 시작·일시정지·재개와 애니메이션은 클라이언트에서 실행한다. 운동 순서, 세트·반복·권장 목표, 설명 콘텐츠와 예상 시간은 서버 결과를 사용한다. 제스처 표현은 클라이언트 UX이며 공식 수행 기록은 해당 plan item의 완료 mutation으로 저장한다.

### 5.12 완료와 미수행 피드백

공식 수행 상태는 앱의 운동 블록 완료 기록으로만 확정한다. 전체 경과 시간은 공식 상태 계산에 사용하지 않는다.

~~~text
COMPLETED
PARTIAL
NOT_COMPLETED
STOPPED_FOR_SAFETY
~~~

웨어러블 또는 외부 운동 기록은 참고 신호로 저장할 수 있으나 위 상태를 확정하거나 덮어쓰지 않는다.

- 모든 계획 블록을 사용자가 완료 체크: COMPLETED
- 하나 이상의 블록을 완료했지만 미완료 블록이 존재: PARTIAL
- 완료 체크한 블록이 없음: NOT_COMPLETED
- 안전 이벤트로 중단: STOPPED_FOR_SAFETY

세트·반복·유산소 권장 시간은 블록의 처방 내용이다. MVP에서는 자동 센서나 경과 시간으로 블록 완료를 추정하지 않고 사용자의 명시적 완료 체크를 신뢰한다.

완료 시:

- 체감 난이도: EASY, APPROPRIATE, HARD
- 통증 발생 여부
- 불편 부위와 심각도
- 이상 반응

미수행 시 가장 큰 이유 하나:

~~~text
TIME_SHORTAGE
FATIGUE
MUSCLE_SORENESS
PAIN
SCHEDULE_CHANGE
LOCATION_EQUIPMENT
WEATHER
DIFFICULTY
LOW_INTEREST
LOW_MOTIVATION
~~~

미수행은 벌점이나 연속 기록 파괴로 표현하지 않는다.

### 5.13 복귀 정책

복귀 모드 조건:

~~~text
마지막 완료 운동 이후 7일 이상
OR
예정 운동 3회 연속 미수행
~~~

정책값:

~~~text
RETURN_MODE_INACTIVITY_DAYS=7
RETURN_MODE_CONSECUTIVE_MISSES=3
~~~

복귀 모드:

- 요청한 첫 세션 시간 유지
- 부하·강도·세트·반복 또는 볼륨 조정
- 익숙한 운동 우선
- 이전 실패 강도를 그대로 복원하지 않음
- 첫 세션 결과 후 단계적 복원

7일과 3회는 의학적 기준이 아닌 MVP 운영 기준이다.

공백 분류는 별도로 유지한다.

- 14일 미만: 일반 공백 또는 복귀 모드 판단
- 14일 이상: 장기 공백으로 표시하고 체크인·복귀 상한을 반드시 재평가
- 1년 이상 서비스 활동 없음: 법정 휴면이 아닌 DORMANT 서비스 분류와 30일 전 통지 후 삭제

### 5.14 마스코트 기본 적용

- 운동 전 변경 이유 브리핑
- 운동 중 3~4개 비방해성 루프
- 운동 후 다음 결정 반영 안내
- 미수행 후 비비난 문구
- 통증·이상 반응 화면에서 장난스러운 표현 중단

마스코트는 안전 문구와 운동 정보를 가리거나 더 눈에 띄게 만들 수 없다.

### 5.15 기본 품질 상태

프론트엔드는 다음 상태를 제공한다.

- 로딩
- 빈 상태
- 네트워크 오류
- 인증 오류
- 권한 거부
- 오래된 체크인
- 선택 불가 옵션
- 안전 중단
- 계정 삭제 대기

### 5.16 주간 리포트와 다음 계획 게이트

- 사용자 timezone 기준 월요일 00:00부터 일요일 23:59까지를 한 주로 계산
- 로그인 여부와 무관하게 날짜 경과로 주가 닫힘
- 닫힌 주에 대해 사용자가 요청할 때 리포트 생성
- 운동 블록 완료 체크 기반 COMPLETED, PARTIAL, NOT_COMPLETED 집계
- 선택적으로 입력한 운동 후 설문과 미수행 이유 반영
- 목표 대비 수행, 조정안 수락, 주요 미수행 이유, 안전 중단 요약
- 리포트 생성 정책과 입력 집계 버전 저장
- 리포트를 생성하고 사용자가 확인하기 전에는 다음 주 계획을 최종 확정하지 않음
- 다음 주 계획 AI 수정은 최대 2회
- 2회 이후 사용자가 직접 편집 가능
- 직접 편집한 계획도 결정적 시간·장소·장비·안전 재검증 필수

주간 리포트 생성과 확인은 핵심 MVP이며 worker나 scheduler 없이 동기 API와 논리적 주 마감으로 구현한다.

## 6. 선택 기능

핵심 흐름 완료 후에만 추가한다.

### 6.1 템플릿 이상의 LLM 설명

### 6.2 추가 웨어러블 제공자

MVP에서 선택한 연동 외 추가 HealthKit·Health Connect 제공자와 확장 데이터는 후속으로 검토한다.

- 권한 거부 시 수동 입력 유지
- 수면, 걸음, 최근 운동, 운동 시간, 안정 시 심박 추세만 사용
- 원시 심박 스트림과 GPS 전체 경로 저장 금지
- 웨어러블만으로 안전 결정 금지
- Expo Go가 아니라 Expo Development Build와 네이티브 설정 사용

### 6.3 날씨

- 야외 운동 가능 여부 보조
- 장애 시 핵심 추천 계속 동작

### 6.4 하루 1회 조정 알림

- 하루 최대 1회
- REST 선택 후 해당 날짜 추가 압박 알림 금지
- 운동 완료 후 알림 금지

알림이 실제 범위에 들어올 때만 queue와 worker 도입을 재검토한다.

## 8. 첫 번째 수직 슬라이스

~~~text
1. Firebase 테스트 사용자 인증
2. 만 14세 이상 이용 자격 확인, 운동 목표, 홈 장소, 장비 입력
3. DOMAIN_APPROVED seed로 기본 상체 40분 루틴 생성
4. 통증 없음, 피로 MODERATE, 희망 운동 시간 40분 확인
5. Training·Recovery·Safety proposal 생성
6. RecoveryAgent가 당일 강도 하향 제안
7. TrainingAgent가 상체 CORE와 운동 순서 유지 주장
8. Coordinator가 40분 요청을 유지한 최종 루틴 1개 선택
9. 최종 루틴 최종 안전 검증
10. 변경 이유 확인
11. 최종 루틴 선택과 0초 경과 타이머 시작
13. 운동 블록을 순서대로 사용자 완료 체크
14. 모든 블록 완료로 COMPLETED 계산
15. 난이도와 통증 저장
~~~

완료 조건:

- 실제 React Native 프론트와 FastAPI 연결
- PostgreSQL과 Alembic 사용
- 목 데이터만으로 동작하지 않음
- agent proposal과 final decision 분리 저장
- 요청 시간을 유지하고 예상 시간 산출 근거에 준비·휴식·전환·마무리 포함
- 완료 상태가 경과 시간이 아니라 운동 블록 체크로 계산됨
- 동일 입력과 규칙 버전에서 같은 결과
- LLM 없이 동작
- 대표 API·통합·골든 테스트 통과

## 9. 대표 데모 시나리오

### A. 정상 수행

~~~text
상태 양호
+ 통증 없음
+ 프로필 희망 시간 확인
+ 장소·장비 충족
-> KEEP
~~~

### B. 강도 다운시프트

~~~text
상체 근력 40분 희망
+ 피로 MODERATE
+ 통증 없음
-> 요청 시간 40분 유지
-> CORE 밀기·당기기와 수행 순서 유지
-> 부하·난이도·세트·반복·휴식 구성 조정
-> 요청 시간 40분을 유지한 최종 루틴 1개 제시
~~~

### C. 사용자의 명시적 시간 변경

~~~text
프로필 기본 희망 시간 40분
-> 사용자가 오늘은 30분으로 직접 변경
-> 당일 requested duration을 30분으로 사용
-> 시스템이 임의로 15분 또는 5분으로 추가 축소하지 않음
~~~

### D. 안전 충돌

~~~text
하체 운동 필요
+ KNEE MILD 또는 MODERATE
+ 집에서 희망 시간 40분
-> DOMAIN_APPROVED 무릎 충돌 운동 제외
-> 검수된 힙브리지·힙힌지·코어 대체
-> CHANGE 또는 RECOVERY
-> 안전 veto된 후보는 최종 루틴으로 반환하지 않음
~~~

### E. 휴식

~~~text
SEVERE 불편 또는 급성 근골격 신호
-> REST
-> final_plan 없음
-> serious tone 안내
~~~

### F. 중대한 이상 반응

~~~text
가슴 불편, 예상하지 못한 심한 숨참, 실신 등
-> STOP_AND_SEEK_HELP
-> 운동 옵션 없음
-> 운동 즉시 중단과 지역 응급의료 도움 안내
~~~

### G. 복귀

~~~text
마지막 완료 후 7일 이상
또는 예정 운동 3회 연속 미수행
-> 복귀 모드
-> 시간·볼륨 축소
-> 익숙한 운동 우선
-> 결과에 따라 단계적 복원
~~~

## 14. 아직 남은 구현 전 세부 결정

- 운동 목표, 경험, 장비, 장소의 전체 머신 코드
- 수면 부족과 운동 부하 누적의 수치 정책

- 운동 중 MILD 또는 MODERATE 불편의 세션 처리
- 외부 안전 검수자 확보와 승인 일정
- 키, 체중, 성별을 실제 UI에서 수집할지 여부

- 체중 기반 칼로리 추정 산식·계수 버전
- 멀티 에이전트 로직 설계 완료 전까지 잠정인 proposal·coordinator·회의 UI 계약

이 항목은 새 제품 요구를 임의로 만들지 않고 담당자 승인 후 관련 계약을 함께 갱신한다.

## 15. 결정 이유와 대안

핵심 MVP는 수동 체크인, 검수된 운동, 결정적 안전·권장 시간 규칙, Training·Recovery·Safety 세 proposal과 Coordinator, 운동 블록 수행 기록, 요청 시 주간 리포트까지 하나의 폐쇄 루프로 묶는다. 제품 가설을 한 주 단위로 실제 검증할 수 있는 최소 범위이기 때문이다.

선택한 범위:

- 웨어러블 요약과 캘린더 연동을 MVP에 포함하되 수동 입력과 특정 요일 비강제 원칙을 유지
- 체중 기반 칼로리 추정치를 참고 정보로 제공

선택하지 않은 대안:

- 장문 LLM 리포트 필수화: 장애 시 핵심 주간 흐름을 막으므로 템플릿 폴백 가능한 설명만 허용
- 정밀 영양·자세 인식·커뮤니티·복잡한 ML: 현재 가설 검증에 필요하지 않아 제외
