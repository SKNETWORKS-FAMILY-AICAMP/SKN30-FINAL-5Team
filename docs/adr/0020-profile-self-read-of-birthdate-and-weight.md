# ADR-0020: 생년월일·체중의 본인 조회 허용

- 상태: ACCEPTED
- 날짜: 2026-09-11
- 소유자: 제품·개발 공동
- 승인 근거: 사용자 명시 요청(2026-09-11). PM·개발팀장 승인 확인
- 관련: ADR-0005(생년월일 연령 확인과 개인정보 처리) 중 "응답 미반환" 결정만 부분 대체
- 관련 문서: `docs/API_CONTRACT.md` 7.2.0, `docs/DATA_MODEL.md` 4.3.3, `docs/DOMAIN_RULES.md`,
  `docs/MVP_SCOPE.md`

## 관계

Supersedes:
ADR-0005 § 보안·개인정보·호환성 영향 중
"생년월일은 API 응답에 반환하지 않는다" 결정만 부분 대체.
ADR-0005의 나머지 결정(암호화 저장, 파생 연령값 미저장, 로그·분석·LLM·에이전트·decision
snapshot 차단, 만 18–64세 eligibility 한정 사용)은 전부 그대로 유지한다.

## 배경

마이페이지 프로필 편집에서 생년월일과 체중을 수정할 때 기존에 저장한 값이 표시되지 않았다.
생년월일은 만 18세 기준 최신 날짜로, 체중은 빈 칸으로 초기화됐다.

원인은 클라이언트가 아니라 읽기 계약이다.

- `PATCH /api/v1/me/settings`는 `date_of_birth`와 `weight_kg`를 이미 받는다.
- `GET /api/v1/me`는 두 값을 모두 반환하지 않는다.

쓰기만 열려 있고 읽기가 닫혀 있어, 클라이언트에는 채울 원본이 존재하지 않았다. 사용자는 값을
확인하려면 수정 화면에서 다시 입력해야 했고, 이는 저장된 값을 덮어쓸 위험을 만든다.

생년월일의 경우 ADR-0005가 "API 응답에 반환하지 않는다"로 못박고 있었다. 이 결정은 생년월일이
결정 입력·로그·LLM으로 확산되는 것을 막으려는 것이었고, 그 목적은 지금도 유효하다. 다만 그
문장이 **본인이 본인의 값을 다시 보는 경로**까지 함께 막고 있었다.

## 결정

**`GET /api/v1/me` 응답에 `date_of_birth`와 `weight_kg`를 추가한다. 대상은 인증된 본인의
프로필뿐이다.**

- 두 필드는 optional이며 기본값은 `null`이다.
- `date_of_birth`는 저장된 암호문을 요청 시점에 복호화해 파생한다. 평문으로 저장하지 않는다.
- 복호화가 불가능한 배포(cipher 미설정, 인증 실패한 envelope)에서는 `date_of_birth`와 `age`가
  함께 `null`이 되고, 프로필 조회 자체는 200으로 성공한다. 생년월일 하나 때문에 마이페이지
  전체가 열리지 않는 상태를 만들지 않는다.
- 암호문(`protected_birthdate`)은 본인에게도 반환하지 않는다.
- `weight_kg`는 이미 평문 컬럼으로 저장돼 있다. 스키마 변경과 마이그레이션이 없다.

### 유지되는 금지 사항

이 ADR은 응답 경로 하나만 연다. 아래는 전부 그대로다.

- 생년월일과 만 나이를 로그·분석 이벤트에 포함하지 않는다.
- 생년월일과 만 나이를 LLM·에이전트 입력으로 전달하지 않는다.
- 생년월일과 만 나이를 decision snapshot에 저장하지 않는다.
- 만 나이는 만 18–64세 eligibility 확인 외에 사용하지 않는다.
- 파생 연령 필드를 DB에 저장하지 않는다.
- 체중은 칼로리 추정 외의 결정 입력으로 사용하지 않는다.
- 계정 삭제·백업 만료 대상에서 생년월일을 제외하지 않는다.

## 결정 이유

본인에게 본인이 입력한 값을 돌려주는 것은 개인정보 확산이 아니다. 확산은 그 값이 결정 입력,
로그, 외부 모델로 흘러갈 때 발생하며, 그 경로는 전부 별도 지점에서 차단돼 있고 이 변경은 그
차단을 건드리지 않는다.

반대로 값을 숨기면 사용자는 수정 화면에서 기억에 의존해 다시 입력하게 된다. 생년월일은 만
18–64세 eligibility의 단일 원본값이므로, 잘못 입력하면 일반 자동 루틴 생성이 차단된다. 값을
가리는 쪽이 오히려 더 큰 위험을 만든다.

복호화는 이미 매 `GET /api/v1/me` 요청에서 만 나이 계산을 위해 수행되고 있었다. 이 변경은 이미
복호화된 값을 버리지 않고 본인에게 돌려주는 것에 가깝고, 새로운 복호화 부담을 추가하지 않는다.

## 검토한 대안

- 체중만 반환하고 생년월일은 계속 숨긴다.
- 생년월일 대신 마스킹한 값(`1997-**-**`)을 반환한다.
- 별도 엔드포인트(`GET /api/v1/me/settings`)를 만들어 편집용 값만 반환한다.

## 선택하지 않은 대안과 이유

- 체중만 열면 생년월일 필드의 문제가 그대로 남는다. 사용자가 보고한 증상의 절반만 해결한다.
- 마스킹한 값은 편집 화면의 기본값으로 쓸 수 없다. 사용자가 결국 전체를 다시 입력해야 하므로
  문제가 해결되지 않는다.
- 별도 엔드포인트는 같은 데이터에 두 개의 읽기 계약을 만든다. 프로필 조회가 이미 존재하고 이미
  복호화를 수행하므로, 엔드포인트를 늘릴 근거가 없다.

## 결과와 영향

`MeProfile` 응답 스키마에 optional 필드 두 개가 추가된다. 기존 필드는 변경되지 않으므로 배포된
클라이언트는 영향을 받지 않는다(additive change).

DB 스키마 변경이 없다. `user_profiles.protected_birthdate`와 `user_profiles.weight_kg`는 이미
존재하며, 마이그레이션이 필요하지 않다.

프론트엔드는 프로필 편집 화면의 초기값을 이 응답에서 채운다. 이때 전송 조건을 "입력했으면
전송"에서 "저장된 값과 다르면 전송"으로 바꿔야 한다. 그렇지 않으면 값을 바꾸지 않은 저장에도
매 요청이 실려 나가 `profile_version`이 불필요하게 올라가고, 목표·기본 시간 변경에 연결된
기존 루틴 폐기가 함께 발생할 수 있다.

## 보안·개인정보·호환성 영향

노출 범위가 "저장소 내부"에서 "인증된 본인"으로 한 단계 넓어진다. 제3자, 다른 사용자, 운영자
조회 경로는 열리지 않는다. 인증은 기존 `get_current_user` 경계를 그대로 사용한다.

암호문은 여전히 반환하지 않으므로 응답이 유출되더라도 키 없이는 저장소의 다른 레코드를 풀 수
없다.

로그·분석·LLM·decision snapshot 차단 지점(`_FORBIDDEN_PAYLOAD_KEYS`, 계정 삭제·인증 로그
마스킹 목록)은 변경하지 않는다. 해당 회귀 테스트를 유지한다.

## 아직 확정되지 않은 사항

- 출시 전 법률·개인정보 검토 결과. `docs/README.md` 5절의 "개인정보 수집·보존" 변경은 출시 전
  법률/개인정보 검토를 요구하며, 이 ADR은 그 검토를 대체하지 않는다.
- 본인 조회 이력을 감사 로그로 남길지 여부. 현재는 남기지 않는다.
- 이미 만 18–64세를 벗어난 프로필의 생년월일 편집 UI. 가입 후 만 65세가 된 사용자는
  저장된 생년월일이 날짜 선택 범위 밖이라 편집 화면에 표시되지 않고, 기존과 같이 기본값이
  놓인다. 체중은 영향받지 않으며 값이 저절로 덮어써지지도 않는다(사용자가 직접 날짜를
  고르기 전에는 전송하지 않는다). 이 케이스는 `ProfileService`의 `AgeRequirementNotMetError`
  주석이 가리키는 D3 미정의 영역과 같은 것으로, 별도 정의 전까지 대응하지 않는다.
  (PM 결정, 2026-09-11.)
