# ADR-0001: 요구사항 기준 문서 및 MVP 범위

- 상태: ACCEPTED
- 날짜: 2026-08-11
- 소유자: 제품·개발 공동
- 승인자: PM + 개발팀장
- 승인 증적: 사용자 명시 승인(2026-08-11, 본 작업 요청). PR 링크는 생성 후 연결
- 관련 요구사항/이슈: `docs/requirements/요구사항_정의서.ndjson`, `docs/TRACEABILITY.md`의 MVP 요구사항 그룹

## 배경

기획서, 요구사항 정의서, 제품 문서 사이에서 기능의 MVP 포함 여부와 최종 사용자 경험을 다르게 해석할 수 있었다. 구현 중 범위가 문서마다 달라지면 API·데이터 모델·테스트가 서로 다른 제품을 기준으로 작성될 위험이 있다.

현재 요구사항 원본에는 47개 상위 그룹과 447개 세부 요구사항이 있으며, WBS 추적표는 세부 요구사항 ID를 1:1로 연결한다. 따라서 제품 범위의 기준 문서와 MVP 공개 경험을 명시적인 구조적 결정으로 고정할 필요가 있다.

## 결정

### 1. 제품 범위 기준

- `docs/requirements/요구사항_정의서.ndjson`을 제품 요구사항과 기능 존재 여부의 기준 문서로 사용한다.
- `docs/MVP_SCOPE.md`는 요구사항 정의서의 MVP 분류를 구현 가능한 포함·제외 범위로 구체화한다.
- `PROJECT_BRIEF.md`는 사용자 문제와 제품 원칙을 설명하는 문서이며, 요구사항 정의서와 MVP_SCOPE의 범위를 임의로 확장하지 않는다.
- 기술·계약 문서가 요구사항 정의서와 충돌하면 구현을 진행하지 않고 해당 문서를 갱신한다.

### 2. MVP에 포함하는 범위

- 만 14세 이상 운동 입문자·복귀자의 가입, 인증, 온보딩과 초기 루틴 생성
- Firebase 인증과 Google·Kakao·Naver 로그인 경로
- 수동 체크인, 운동 계획 조정, 운동 블록 실행·완료·미수행 피드백
- Training·Recovery·Safety 세 proposal과 Coordinator의 최종 통합, 독립된 최종 안전 검증
- 웨어러블 일별 요약 입력 경로와 권한 거부·미연동 시 수동 입력 폴백
- 캘린더 빈 시간 후보와 운동 계획 등록. 캘린더 데이터는 공식 운동 수행 상태를 변경하지 않는다.
- 운동 후 피드백, 요청형 주간 리포트, 리포트 확인 후 다음 계획 게이트
- 가입 후 14일 AI 코치 무료 체험. Premium 결제·구독은 MVP 이후로 분리한다.
- 운동 종류·시간·강도와 사용자 체중을 이용한 예상 소모 칼로리 추정치. 체중이 없으면 추정값을 제공하지 않으며, 해당 값은 진단·안전 판정의 단독 근거로 사용하지 않는다.

### 3. MVP 공개 경험

- 사용자에게 제공하는 최종 운동 루틴은 한 개다.
- `lighter`와 `original`은 공개 선택지로 제공하지 않는다. 내부 후보와 안전 검증 기록으로만 관리한다.
- `REST`와 `STOP_AND_SEEK_HELP`에는 운동 계획을 제공하지 않는다.
- 사용자의 요청 운동 시간은 시스템이 임의로 축소하지 않는다. 다운시프트는 부하·강도·세트·반복·운동 유형·휴식 구성을 조정한다.

### 4. MVP에서 제외하거나 후속으로 미루는 범위

- F012~F023 확장 기능(기능 제안, 영상·리워드·커머스·광고·AI 상담·영양 등)
- 정밀 칼로리 계산, 식단 분석, 질환 진단·치료·재활 처방과 의료적 운동 처방
- MVP에서 선택한 provider 외 추가 웨어러블·캘린더 provider
- 날씨 연동, 푸시 알림, 결제 연동, 실시간 생체 신호 제어
- 에이전트별 마이크로서비스, 벡터 데이터베이스, 대규모 RAG
- LLM을 필수 계획 생성기 또는 안전 판정기로 사용하는 방식

## 결정 이유

- 요구사항 ID와 WBS·인수조건·테스트 연결을 한 기준으로 유지해 범위 누락과 중복을 줄인다.
- 최종 루틴 하나만 공개하면 안전 검증, 선택 API, 운동 세션 생성의 계약을 단순하게 유지할 수 있다.
- 웨어러블과 캘린더는 요구사항에 포함하되 수동 폴백과 공식 수행 상태 분리를 유지해 핵심 흐름의 접근성과 재현성을 보장한다.
- 체중 기반 칼로리 추정치를 참고 정보로 제한하면 사용자에게 유용한 기록을 제공하면서 의료적 오해와 안전 판정 오용을 줄일 수 있다.
- 확장 기능과 정밀·의료 기능을 분리해 MVP 가설을 먼저 검증하고, 후속 변경의 영향 범위를 통제한다.

## 검토한 대안

1. 기존 기획서 또는 `PROJECT_BRIEF.md`를 단독 범위 기준으로 사용
2. `primary`, `lighter`, `original` 세 가지 계획을 MVP 공개 선택지로 제공
3. 웨어러블·캘린더를 MVP 이후로 미루고 수동 입력만 제공
4. 모든 요구사항 그룹을 MVP에 포함해 초기부터 확장 기능까지 구현

## 선택하지 않은 대안과 이유

- 기존 기획서 또는 PROJECT_BRIEF 단독 기준: 요구사항 정의서의 세부 ID·MVP 표기와 충돌할 수 있고 추적성이 약하다.
- 세 가지 계획 공개: 최종 루틴 하나를 제공한다는 제품 범위와 충돌하고 안전 veto·선택 계약을 복잡하게 만든다.
- 웨어러블·캘린더 제외: 요구사항 정의서의 웨어러블·캘린더 MVP 요구를 충족하지 못한다. 대신 미연동·권한 거부 폴백을 필수로 둔다.
- 전체 기능 동시 구현: MVP 검증 가설과 팀의 구현 범위를 넘어가며 안전·개인정보 검토 범위를 불필요하게 확장한다.

## 결과와 영향

긍정적 영향:

- 이후 DOMAIN_RULES, API_CONTRACT, DATA_MODEL, TEST_STRATEGY는 이 ADR의 범위를 기준으로 정합성을 검토한다.
- F012~F023을 MVP 작업에 섞지 않고 별도 확장 추적 상태로 관리할 수 있다.
- 최종 루틴·REST·안전 중단의 공개 계약을 한 가지 사용자 경험으로 고정한다.

부정적 영향:

- 웨어러블·캘린더 provider, 칼로리 산식·계수, 일부 사용자 문구는 추가 결정이 필요하다.
- MVP 범위를 변경하려면 이 ADR을 직접 수정하지 않고 새 ADR에서 `SUPERSEDES` 관계를 남겨야 한다.

## 보안·개인정보·호환성 영향

- 만 14세 미만 가입을 차단하고 정확한 생년월일은 수집하지 않는다.
- 일반·민감·웨어러블·캘린더·마케팅 동의를 분리하며, 동의 철회 시 해당 처리와 외부 동기화를 중단한다.
- 칼로리 추정치는 체중 기반 추정치로만 제공하고 진단·안전 판정의 단독 근거로 사용하지 않는다.
- 인증 토큰, 직접 식별자, 원시 건강·웨어러블 데이터를 LLM 또는 로그에 전달하지 않는다.
- 공개 API와 기존 호환 필드는 별도 API ADR에서 하위 호환 원칙을 지키며 확정한다. 이 ADR은 공개 필드의 세부 스키마를 결정하지 않는다.

## 아직 확정되지 않은 사항

- 멀티 에이전트 proposal·Coordinator·회의 UI의 상세 입력·출력 스키마와 조정 순서
- MVP에서 채택할 웨어러블·캘린더 provider와 세부 payload
- 체중 기반 칼로리 추정 산식·계수·단위·반올림 기준
- 외부 안전·개인정보 검수 일정과 최종 승인 증적

## 후속 작업

1. 승인 증적을 PR 또는 회의 결정 링크로 보강한다.
2. `MVP_SCOPE.md`, `PROJECT_BRIEF.md`, `TRACEABILITY.md`의 관련 문서에 ADR 번호를 연결한다.
3. 별도 ADR에서 멀티 에이전트 협업 상세, 외부 연동·API·데이터 계약, 안전·개인정보 정책을 각각 기록한다.
4. 범위 변경이 생기면 요구사항 원본과 WBS를 먼저 갱신하고, 영향받는 문서와 ADR 관계를 함께 갱신한다.
