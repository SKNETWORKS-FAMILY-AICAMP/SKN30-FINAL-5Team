# ADR-0003: 외부 연동·인증·API·데이터 구조 경계

- 상태: ACCEPTED
- 날짜: 2026-08-11
- 소유자: 제품·개발 공동
- 승인자: 프론트엔드 + 백엔드 + 개발팀장(개발 단계 승인)
- 승인 증적: 사용자 명시 승인(2026-08-11, 본 작업 요청). PR 링크는 생성 후 연결
- 관련 요구사항/이슈: `F003`, `F004`, `F010`, `F025`, `NFR-005`

## 배경

요구사항 정합성을 위해 소셜 인증, 웨어러블 API와 동의·연동·결정 데이터를 문서에 반영했다. 수동 외부 기록 API는 후속 기능 검토 대상으로 분리하며 provider, payload와 실제 저장 스키마는 아직 논의 중이다.

## 결정

- Firebase ID Token을 서비스 세션 권한의 기준으로 둔다.
- Google은 Firebase 기본 provider, Kakao·Naver는 provider adapter 경계로 문서화한다.
- 웨어러블은 보조 입력 경로이며 미연동 시 수동 체크인 경로를 유지한다.
- 수동 외부 운동 기록은 MVP에 포함하지 않고 추후 기능으로 분류한다.
- 공개 API는 `/api/v1`와 Pydantic 계약으로 관리하고, 동의·연동·proposal·최종 결과를 분리 저장하는 방향으로 문서화한다.
- provider 세부 payload, DB 컬럼, migration과 호환성은 데이터 확정 후 에이전트 설계와 개발 단계에서 확정한다.

## 결정 이유

요구사항에 명시된 외부 연동을 추적하면서도 provider 선택과 데이터 계약을 성급하게 동결하지 않기 위해서다.

## 검토한 대안

- 외부 provider를 MVP에서 모두 제외
- provider별 세션과 도메인 로직을 직접 결합
- 현재 문서의 API·DB 예시를 최종 계약으로 간주

## 선택하지 않은 대안과 이유

- 외부 연동 제외는 MVP 요구사항과 수동 체크인 폴백 경로를 충족하지 못한다.
- provider 직접 결합은 교체·테스트·보안 경계를 약화한다.
- 잠정 예시를 최종 계약으로 간주하면 데이터 확정 후 재작업이 발생한다.

## 결과와 영향

문서 간 인증·연동·저장 상위 경계는 이 ADR로 승인한다. 이 ADR만으로 provider별 API와 DB schema를 동결하지 않으며, 상세 계약 확정 시 API·DATA_MODEL·migration·호환성 테스트를 함께 갱신한다.

## 보안·개인정보·호환성 영향

provider token 원문, GPS·직접 식별자·초 단위 심박과 같은 고해상도 웨어러블 샘플은 저장·로그·LLM 입력에서 제외한다. 정규화와 품질 검증에 필요한 최소 provider 원본 payload는 암호화하고 접근을 제한해 최대 24시간 임시 보관할 수 있으며, 로그·LLM·공개 응답에는 포함하지 않는다. 공개 필드는 하위 호환 원칙을 적용한다.

## 아직 확정되지 않은 사항

- MVP provider와 OAuth 세부 방식
- 웨어러블 요약 필드·품질·출처·라이선스
- 동의 버전, migration과 외부 장애 재시도 계약

## 후속 작업

1. 외부 데이터 항목과 provider를 확정한다.
2. 확정 데이터를 기준으로 에이전트 입력 스냅샷을 설계한다.
3. 구현 전에 API·DB·보안·호환성 상세 계약 승인을 완료하고, 상위 경계가 달라지면 새 ADR을 작성한다.
