# ADR-0018: 통증 제외 단일 기준과 사용자 편집 경계

- 상태: ACCEPTED
- 날짜: 2026-09-03
- 소유자: 제품·개발 공동
- 승인 근거: 사용자 명시 결정(2026-09-02, 2026-09-03)
- 관련: ADR-0015, ADR-0017, `SERVICE_POLICY_SAFETY_AND_ADAPTATION_V1.md`

## 배경

코어 루프를 구현 가능한 수준으로 좁히는 과정에서 다섯 개의 미확정 지점이 남았다. 각각 코드를
쓰기 전에 답이 필요했고, 나중에 뒤집히면 마이그레이션과 검수 데이터를 되돌려야 하는 항목이었다.

1. 통증 기반 운동 제외 관계를 어디에 둘 것인가.
2. 체감 난이도 `HARD` 피드백이 다음 루틴의 무엇을 낮추는가.
3. 만 18–64세 범위 밖 기존 가입자를 어떻게 처리하는가.
4. 사용자가 직접 고친 세트·반복이 무엇을 다시 통과해야 하는가.
5. 사용자의 운동 순서 변경을 어디까지 허용하는가.

## 결정

### D1. `exercise_safety_rules`가 통증 기반 제외의 Single Source of Truth다

- `exercise_contraindicated_pain_regions` 테이블을 신규 생성하지 않는다.
- `exercise_load_regions`도 만들지 않는다. 배포 중인 규칙이 전부 운동 단위(`rule_scope=EXERCISE`)로
  부위 관계를 직접 보유하므로, 카탈로그에 부위 속성을 다시 두면 같은 정보를 두 벌 관리하게 된다.
- 카탈로그는 운동 자체의 속성만 갖는다. `이 운동은 허리 통증 시 제외`와 같은 최종 판정값을 카탈로그에
  중복 저장하지 않는다. 정책 변경은 `exercise_safety_rules` 수정으로만 처리한다.
- 복수 통증 부위는 각각 독립 판정하고, 하나의 부위에서라도 `EXCLUDE`가 발생하면 해당 운동을 제외한다.
- 한 운동에 여러 규칙이 걸리면 가장 보수적인 결과를 우선한다. 구현된 효과 코드는 `EXCLUDE`와
  `CAUTION` 둘이므로 우선순위는 `EXCLUDE > CAUTION > 규칙 없음`이다.
- Safety 필수 정보가 없거나 검수가 완료되지 않은 운동은 추천 후보에 포함하지 않는다(fail-closed).

판정 흐름은 `DOMAIN_RULES.md` 4.3.1이 이미 규정한 그대로다. 이 ADR은 데이터를 어디에 둘지만 확정한다.

### D2. 어려움 피드백은 난이도 → 강도 → 시간 배분 순으로 낮춘다

- `difficulty_code=HARD`일 때 `VOLUME_HIGH`·`MOVEMENT_DIFFICULT`를 하나 이상 복수 선택으로 받는다.
- 하나만 선택하면 해당 축을 한 단계 낮춘다. 둘 다면 운동 난이도를 먼저 조정한다.
- 더 낮은 난이도나 variant가 없으면 강도 하향으로 전환한다.
- 강도 조절만으로 대응하기 어려우면 시간 배분을 조정한다. **이 단계는 요청 시간을 줄이지 않는다.**
  `DOMAIN_RULES.md` 5절이 허용하는 ±300초 창 안에서 요청값보다 짧은 쪽 계획을 선택하는 것까지만
  허용한다.
- 한 번의 조정에서는 하나의 축만 변경하고 다음 수행 피드백으로 효과를 평가한다.

### D3. 범위 밖 기존 가입자는 차단을 먼저 적용한다

- 만 18–64세 범위 밖 사용자는 루틴 생성·Daily Check-in·결정 실행·운동 세션 시작을 차단한다.
- 로그인, 조회, 계정 설정, 계정 삭제는 계속 사용할 수 있어야 한다.
- 서버는 eligibility 판정만으로 계정을 자동 삭제하지 않는다. 기존 가입자 정리가 필요하면 차단을
  적용한 뒤 별도 승인과 릴리스로 진행한다.
- 이용약관에 연령·질병·장애 관련 고지를 추가한다. 문구는 진단·치료·처방 표현을 피하고 서비스
  지원 범위 밖이라는 사실만 서술한다.

### D4. 사용자 편집은 시간 검사 하나만 면제한다

- 사용자가 세트 수 또는 반복 수를 직접 수정한 revision에 한해 요청 시간 ±300초 검사를 면제한다.
- **면제되는 것은 `REQUESTED_DURATION_MISMATCH` 하나뿐이다.** integrity validator의 나머지 검사는
  그대로 적용한다.
- 서버는 해당 revision을 사용자 편집본으로 표시하고 적용된 면제를 재현 기록에 남긴다.

### D5. 운동 순서 변경은 같은 phase 안에서만 허용한다

- `WARMUP`·`MAIN`·`COOLDOWN` 경계를 넘는 이동은 `PHASE_BOUNDARY_VIOLATION`으로 거부한다.
- phase 안에서 재배치한 뒤 전체 `sequence`를 1부터 연속으로 다시 매긴다.

## 이유

**D1.** 배포 중인 v2.0.5 번들에 이미 규칙 595건이 `DOMAIN_APPROVED` 상태로 들어 있고, 11개 부위를
덮으며, 카탈로그 162개 운동이 빠짐없이 최소 1개 규칙을 갖는다. 같은 의미의 금기 관계를 새 테이블로
옮기면 검수를 통과한 데이터를 다시 만들어야 하고, 두 소스가 갈라질 때 어느 쪽이 옳은지 판단할
근거가 사라진다.

fail-closed는 이미 스키마가 강제한다. `exercises`와 `exercise_safety_rules` 모두
`review_status_code`를 `DOMAIN_APPROVED`로 제한하는 CHECK 제약을 갖고 있어 미검수 레코드는 애초에
저장되지 않는다. 따라서 이 규칙을 명문화해도 후보 풀이 줄어들지 않는다.

**D2.** 시간 축소를 후순위 조정 수단으로 두면 `AGENTS.md` 7절의 "시스템은 사용자의 명시적 입력 없이
시간을 더 줄이지 않는다"와 부딪힌다. 게다가 ADR-0017 이후 1회 운동시간은 매일 Daily Check-in에서
사용자가 직접 입력하므로, 시스템이 줄일 수 있는 시간이라는 개념 자체가 거의 남지 않는다. ±300초 창의
아래쪽을 선택하는 것으로 한정하면 조정 의도는 살리면서 불변식을 유지할 수 있다. 이 창은 이미 5절이
승인한 범위다.

**D3.** 삭제와 차단은 되돌릴 수 있는 정도가 다르다. 판정 기준이 한 번 더 바뀔 수 있고, 삭제는 복구
경로가 없다. 차단을 먼저 적용하면 같은 목적을 달성하면서 되돌릴 여지를 남긴다.

**D4.** 요청 시간은 사용자가 원하는 운동량의 근사값이고, 사용자가 세트·반복을 직접 고치는 행위는 그
근사값보다 더 명시적인 입력이다. 다만 `validate_plan_integrity`는 ADR-0015의 골든 시나리오 6이
지정한 안전 veto 집행 지점이기도 하다. 같은 함수가 안전 제외 운동 포함과 승인 pool 이탈을 함께
검사하므로, 사용자 편집이라는 이유로 validator 전체를 건너뛰면 안전 검증까지 함께 꺼진다. 따라서
면제 범위를 위반 코드 하나로 못 박는다.

**D5.** 계획 항목은 이미 `phase_code`를 갖고 `WARMUP`·`MAIN`·`COOLDOWN` CHECK 제약과
`(routine_day_id, phase_code, sequence)` 인덱스가 있다. phase 경계를 지키는 제약은 새 스키마 없이
구현할 수 있고, 준비운동이 마무리 뒤로 가는 상태를 원천 차단한다.

## 영향

- `DOMAIN_RULES.md`: 6.1 어려움 피드백 조정 사다리 신설, 10절 feedback 계약에 이유 코드 추가,
  11.2의 `USER` revision 검증 규칙 갱신.
- `API_CONTRACT.md`: 12.6 feedback 요청에 `difficulty_reason_codes` 추가, `USER` 편집 계약에 시간 검사
  면제와 phase 경계 제약 추가, eligibility 차단 범위 명시.
- `DATA_MODEL.md`: 카탈로그 확장 목록에서 `exercise_load_regions`·`exercise_contraindicated_pain_regions`
  제거, `exercise_safety_rules`를 SSOT로 명시, `workout_feedback_difficulty_reasons` 신설.
- `TEST_STRATEGY.md`: 골든 94–98과 불변식 3건 추가.
- `AGENTS.md` 7절은 변경하지 않는다. D2가 불변식 안에 들어오도록 해석을 좁혔기 때문이다.

## 후속 작업

- `workout_feedback_difficulty_reasons` 마이그레이션은 온보딩·체크인 마이그레이션 뒤 순번으로 만든다.
- 조정 사다리를 결정 경로에 연결하려면 `perceived_difficulty_code`가 workouts 모듈 밖으로 나가야 한다.
  현재는 저장·조회만 되고 결정 입력에 도달하지 않는다.
- 배포 중인 규칙은 `MODERATE`와 `SEVERE`를 구분하지 않는다. 두 심각도의 제외 결과가 모든 부위에서
  동일하므로, NRS 3단계 구분이 실제로 다른 결과를 내려면 규칙 데이터를 먼저 확장해야 한다.

## 미확정

- 이용약관 개정 문구와 법무 검토 일정.
- 범위 밖 기존 가입자의 최종 정리 방식과 시점.
- 사용자 편집 revision의 최소 요청 필드와 낙관적 잠금 오류 코드(`API_CONTRACT.md` 14절 질문 유지).
