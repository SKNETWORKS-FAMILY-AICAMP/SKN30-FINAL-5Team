# ADR-0019: 웨어러블 연동 폐기와 확장 여지 보존

- 상태: ACCEPTED
- 날짜: 2026-09-07
- 소유자: 제품·개발 공동
- 승인 근거: 사용자 명시 요청(2026-09-07, 게이트 G2)
- 관련: ADR-0016(외부 캘린더 폐기), `AGENTS.md` 7절·11절
- 관련 작업: `docs/tasks/2026-09-improvements/` BL-3, FE-13

## 배경

웨어러블 연동은 온보딩 동의 항목, 마이페이지 "연동 기기" 행, 계정 화면의 동의 토글로 사용자에게
노출돼 있었으나 실제 연동 구현은 없었다. 존재하지 않는 기능에 동의를 받고 있었던 셈이다.

동시에 `AGENTS.md` 11절은 골든 시나리오 4번 "웨어러블 데이터 없음 → 수동 체크인 폴백"을 필수
테스트로 요구한다. 계약을 전부 삭제하면 이 시나리오가 사라지고, `daily_contexts`에 이미 저장된
`sleep_source_code = 'WEARABLE'` 행을 읽을 수 없게 된다.

## 결정

**사용자에게 보이는 웨어러블 표기를 전부 제거하고, 데이터 계약은 확장 여지로만 남긴다.**

### 제거

- 온보딩의 웨어러블 연동 동의 입력.
- 마이페이지 "연동 기기" 행과 계정 화면의 "웨어러블 연동" 동의 토글.
- 웨어러블을 언급하는 사용자 대상 문구 일체.
- `WEARABLE_INTEGRATION`을 신규 수집 대상으로 취급하는 동작. 요청이 값을 보내더라도 적용하지
  않고 항상 미동의로 저장한다.

### 유지

- `ConsentTypeCode.WEARABLE_INTEGRATION` 값. 기존 동의 기록이 이 코드를 참조한다.
- `sleep_source_code`의 `MANUAL | WEARABLE` 값 도메인. 기존 체크인 행이 이 값을 쓰고 있다.
- 골든 시나리오 4번과 수동 체크인 폴백 경로.
- 웨어러블 데이터를 안전 판정의 단독 근거로 쓰지 않는다는 기존 금지 규칙.

### 요청 필드

`ConsentValues.wearable_integration`은 요청 스키마에 남긴다. 이 모델은 `extra="forbid"`이므로
필드를 지우면 배포된 클라이언트의 요청이 무시가 아니라 422가 된다. 값은 받되 적용하지 않는다.

같은 이유로 ADR-0016이 폐기한 `CALENDAR_INTEGRATION`도 같은 처리를 적용한다. 두 항목은 이제
"폐기된 동의"라는 하나의 범주로 관리한다.

## 이유

값 도메인을 좁히는 것과 화면에서 없애는 것은 별개다. 요구사항은 후자였고, 전자는 기존 데이터와
필수 테스트를 깨뜨린다. 코드 값을 남겨도 사용자에게 노출되지 않으므로 "현재 서비스에는 표시 안 됨"
요구를 그대로 만족한다.

`AGENTS.md` 7절의 "웨어러블 없는 사용자를 지원해야 한다"는 불변식은 이 결정으로 강화된다. 모든
사용자가 수동 체크인 경로를 쓴다.

## 선택하지 않은 대안

- **`WEARABLE_INTEGRATION` 코드와 `sleep_source_code='WEARABLE'` 삭제**: 가장 깨끗해 보이지만
  기존 동의 기록과 체크인 행이 읽히지 않게 되고, 골든 시나리오 4번을 다시 써야 한다. 되돌릴 때
  비용도 가장 크다.
- **동의 기록을 아예 쓰지 않음**: "동의하지 않음"과 "묻지 않음"이 구분되지 않는다. 미동의로
  기록하는 편이 사실에 가깝다.

## 영향

- 기존 `WEARABLE_INTEGRATION` 동의 기록은 삭제하지 않는다. 조회와 계정 삭제 경로는 그대로 동작한다.
- 이미 동의했던 사용자의 상태는 다음 온보딩 쓰기 시점에 미동의로 갱신된다. 연동 기능이 없으므로
  실질적 권한 변화는 없다.
- 웨어러블을 다시 도입하려면 이 ADR을 대체하는 새 ADR과 실제 연동 설계가 필요하다.

## 미확정 사항

- 폐기된 동의 유형을 언제 코드 값에서 제거할지. 기존 기록 보존 기간 정책이 정해진 뒤 판단한다.
