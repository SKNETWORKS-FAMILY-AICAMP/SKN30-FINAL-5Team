# ADR-0005: 생년월일 기반 연령 확인과 개인정보 처리

> 상태 메모(2026-09-02): 만 14세 기준과 프로필 만 나이 표시는 최신 서비스 정책의 만 18–64세
> eligibility 계약으로 대체됐다. 생년월일 암호화·파생 연령값 최소화 원칙만 현재 기준으로 유지한다.

## 배경

기존 온보딩은 연령대와 성인 확인값을 사용했으나, 만 18–64세 서비스 지원 범위를 서버에서 일관되게 확인하고 불필요한 파생값 저장을 막기에 충분하지 않았다. 생년월일을 적격성 확인에 필요한 최소 원본값으로 정의하고, 민감한 원본값의 처리 경계를 별도로 고정할 필요가 있다.


## 결정

- 생년월일만 연령 관련 원본값으로 수집하고 암호화해 저장한다. 파생 연령 필드는 저장하지 않는다.
- 서버는 사용자 timezone의 로컬 날짜를 기준으로 만 나이를 일시 계산한다.
- 만 나이는 만 18–64세 eligibility 확인 외에 사용하거나 표시하지 않는다.
- 생년월일과 만 나이는 로그·분석·LLM·에이전트·decision snapshot에서 제외한다.
- 생년월일은 수정할 수 있으며, 범위를 벗어나게 변경하면 일반 자동 루틴 생성을 차단한다.
- 암호화 방식, 키 관리, 접근 제한의 구체 구현은 클라우드 확정 후 결정한다.
- 기존 계정 삭제·백업 만료 정책을 적용한다.
- MET 및 운동 강도 정책은 변경하지 않는다.

## 결정 이유

생년월일을 단일 원본값으로 사용하면 사용자 timezone의 로컬 날짜를 적용한 만 18–64세 eligibility를 재현할 수 있다. 파생값을 저장하지 않고 생년월일의 downstream 전달을 차단하면 클라이언트 조작과 불필요한 개인정보 확산을 함께 줄일 수 있다.

## 검토한 대안

- 연령대만 입력받고 사용자가 지원 연령대임을 직접 확인
- 연령 관련 파생값을 클라이언트 입력값으로 저장
- 생년월일을 저장하지 않고 가입 시점에만 일회성 확인

## 선택하지 않은 이유

- 연령대만 입력받는 방식은 경계일의 만 나이 계산과 재현이 어렵다.
- 클라이언트 파생값을 신뢰하면 지원 범위 차단을 우회할 수 있다.
- 생년월일을 저장하지 않으면 프로필 조회·온보딩 갱신 시 만 나이와 이용 자격을 재검증할 수 없다.

## 결과와 영향

온보딩 요청은 필수 `date_of_birth`를 사용하고 API·데이터·테스트 계약은 서버의 일시 계산 규칙을 기준으로 한다. `user_profiles`에는 생년월일만 암호화해 저장하며 프로필 서비스만 접근한다. 프로필 응답에는 계산된 만 나이를 표시하지 않고, 구현 시 생년월일과 만 나이를 decision snapshot, 분석 이벤트, 로그, LLM·에이전트 입력으로 전달하지 않는다.

## 보안·개인정보·호환성 영향

생년월일은 API 응답에 반환하지 않고 애플리케이션 로그와 분석 이벤트에 포함하지 않는다. 계정 삭제 시 운영 DB에서 7일 이내 삭제하고 백업은 30일 이내 만료한다. 구체적인 암호화·키 관리·접근 제한 구현은 클라우드 확정 전까지 결정하지 않는다.

## 아직 확정되지 않은 사항

- 생년월일 암호화 키 관리와 프로필 서비스 접근 제어의 구체 구현
- 출시 전 법률·개인정보 검토 결과와 보존 예외
- 출시 전 생년월일 변경 재검증 UX와 차단 상태의 복구 절차

## 후속 작업

1. API·데이터 모델·도메인·테스트 계약에 생년월일과 서버 일시 계산 규칙을 반영한다.
2. 구현 시 계정 삭제·백업 만료 작업에 생년월일을 포함한다.
3. 출시 전에 암호화·접근 제한·개인정보 처리 절차를 검토하고 승인 증적을 연결한다.
