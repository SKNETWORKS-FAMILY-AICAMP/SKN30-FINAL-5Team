# 싱글 에이전트와 멀티 에이전트의 서비스 적합성 비교

## 현재 상태

- 비교 브랜치: `eval/single-vs-multi-agent`
- 비교 모델: `gpt-5.4`
- 하네스: `single-multi-agent-suitability-v2`
- 상태: 설계 및 오프라인 검증 완료, 라이브 반복 실행 대기
- 이전 v1 결과: 참고용으로만 보존하며 아키텍처 우열의 근거로 사용하지 않음

v1은 싱글 조건에 Training 역할만 부여하고 멀티 조건에는 deterministic fallback을
포함했다. 따라서 역할 범위와 복구 정책이 달라 공정한 아키텍처 비교가 아니었다.

## 검증할 질문

우리 서비스에서 멀티 에이전트가 적합하다는 주장은 단순히 호출 성공률이 높다는 뜻이
아니다. 다음 세 조건을 함께 만족해야 한다.

1. 건강한 기본 상황에서는 통합형 싱글 에이전트보다 품질이 저하되지 않는다.
2. 목표, 회복 상태, 시간 제약이 동시에 충돌하는 상황에서는 역할 분리가 실행 가능한
   계획을 더 안정적으로 만든다.
3. 추가 호출 수와 지연 시간을 감수할 정도로 계획 품질의 차이가 블라인드 평가에서도
   확인된다.

안전 veto는 두 조건 모두 동일한 deterministic 사전 게이트와 사후 integrity validator를
사용한다. 따라서 이 실험은 멀티 에이전트가 더 안전하다고 주장하지 않는다. 비교 대상은
안전 경계 안에서의 계획 조정 능력이다.

## 비교 조건

### 통합형 싱글 에이전트

한 번의 구조화 출력 호출이 Training, Recovery, Feasibility의 책임을 모두 수행하고 최종
계획을 만든다. 멀티 에이전트 전용 prompt를 재사용하지 않고 별도의 통합 prompt를 사용한다.

### 역할 분리형 멀티 에이전트

Training이 운동 계획을 제안하고 Recovery와 Feasibility가 조정 코드를 제안한다. Coordinator가
세 제안을 하나의 계획으로 통합한다. 이는 현재 서비스의 V3 그래프와 동일한 책임 분리다.

두 조건은 같은 GPT-5.4 모델, 운동 pool, ConstraintEnvelope, compiler, 실제 카탈로그 시간 계산,
integrity validator를 사용한다. 순수 아키텍처 비교를 위해 deterministic fallback은 양쪽 모두
비활성화한다.

## 시나리오와 반복

| 그룹 | 시나리오 | 검증 목적 |
|---|---|---|
| 기본 | 일반 체력·30분·정상 회복 | 단순 상황 비열화 여부 |
| 기본 | 근력 증가·30분·정상 회복 | 목표가 달라도 기본 품질 유지 여부 |
| 단일 제약 | 일반 체력·20분 | 시간 적합성 |
| 단일 제약 | 일반 체력·30분·피로 | 회복 조정 적합성 |
| 복합 제약 | 일반 체력·20분·피로 | 시간과 회복의 동시 조정 |
| 복합 제약 | 근력 증가·30분·피로 | 목표 보존과 회복의 동시 조정 |

각 시나리오는 3회 반복한다. 호출 순서 효과를 줄이기 위해 시나리오와 반복 번호에 따라
싱글 우선과 멀티 우선 실행을 교차한다.

## 자동 평가 지표

실행 가능한 계획은 다음 조건을 모두 만족해야 한다.

- 모델 호출과 구조화 출력 성공
- deterministic integrity validation 통과
- WARMUP, MAIN, COOLDOWN 전체 포함
- MAIN에 해당 목표의 CORE 운동 포함
- 정상 회복은 `KEEP`, 피로 상황은 `DOWNSHIFT` 선택
- 요청 시간과 실제 카탈로그 기반 계산 시간의 허용 오차 충족

추가로 provider 호출 수, 입력·출력 토큰, 지연 시간, 회복 적합 운동 비율을 별도 기록한다.
비용은 승인된 가격 기준이 없으므로 임의 계산하지 않는다.

## 사전 결정 기준

자동 근거가 역할 분리를 지지하려면 아래 두 조건을 모두 만족해야 한다.

- 기본 그룹 6회에서 멀티의 실행 가능 계획 수가 싱글보다 1건 넘게 낮지 않을 것
- 복합 제약 그룹 6회에서 멀티가 싱글보다 실행 가능 계획을 최소 2건 더 만들 것

두 번째 기준은 복합 제약 그룹에서 최소 33%p의 성공 차이를 요구한다. 표본이 작으므로 이는
통계적 일반화가 아니라 다음 단계 투자 여부를 정하는 사전 정의된 제품 실험 기준이다.

## 블라인드 전문가 평가

양쪽 모두 성공한 동일 시나리오·동일 반복 계획만 A/B 후보로 내보낸다. 평가 파일에는
아키텍처 이름을 넣지 않고 별도 blind key에만 매핑을 보관한다. 전문가는 다음 항목을 평가한다.

- 목표 보존
- 회복 상태에 대한 적절성
- 시간·장소 기준 실행 가능성
- 종합 선호

자동 기준을 통과하더라도 전문가 평가가 끝나기 전 최종 결론은
`PENDING_BLIND_EXPERT_REVIEW`이다. 이 구조는 “멀티가 더 적합하다”는 결론을 코드 성공률만으로
과장하지 않기 위한 것이다.

## 생성 산출물

- `results.json`: 원시 결과, 자동 집계, 사전 결정 기준 결과
- `summary.md`: 핵심 지표 요약
- `expert_review_template.jsonl`: 아키텍처 라벨을 제거한 A/B 평가 자료
- `blind_key.json`: 평가 완료 후에만 열어볼 A/B 매핑

## 라이브 실행 전 남은 사항

6개 시나리오를 3회 반복할 때 보수적인 상한은 216 provider 호출이다. 이는 각 역할 호출이
설정상 최대 2회 시도될 수 있다고 가정한 상한이며 실제 호출 수는 더 적을 수 있다. 이 호출
예산 승인을 받은 뒤 스테이징 one-shot 환경에서 실행하고 이 문서에 결과와 해석을 추가한다.
